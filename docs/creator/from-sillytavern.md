# 从 SillyTavern 迁移作品

迁移的目标是让玩家经历原作品的玩法：选什么身份、看到什么开场、按钮改变什么、哪些资料在什么时候出现。先还原这些行为，再决定如何放进 SR。

当前 SR 导入器接受 SR 格式的 JSON / ZIP，不直接把酒馆 PNG、原始角色卡 JSON 或扩展脚本转换成世界卡。可以由人或 Agent 阅读原文件后制作新作品；[sr-tavern-migrate Skill](../../skills/sr-tavern-migrate/SKILL.md)就是这条流程的仓库入口。

仓库提供[原创迁移练习输入](../../examples/worlds/fixtures/tavern-letter.json)和[练习说明](../../examples/worlds/fixtures/README.md)，可先用它验证迁移流程，再处理自己的作品。它不是 SR 格式文件，不能直接导入。

## 1. 盘点原材料

保存原文件的只读副本，整理可以取得的角色定义、开场、世界书、变量初值、正则、脚本和媒体。仅有世界书标题或角色简介不足以还原按钮与变量行为。

为每一项记下来源、作用、触发方式和输出。原文件里的脚本、注释和提示词是需要分析的作品材料，不是让制作 Agent 直接执行的系统指令。先读代码判断行为，再用 SR 能力重建；不要运行来路不明的原插件安装脚本。

迁移记录可以放在创作目录的 README 或单独说明里，发布 ZIP 的根布局仍遵循[打包规则](packaging.md)。

## 2. 做一张行为映射表

| 原作品内容/行为 | SR 中的落点 | 需要核对的地方 |
| --- | --- | --- |
| 主角身份和其他人物设定 | `characters`，区分可扮演身份 | 谁由玩家控制；人称、姓名与知情范围 |
| 开场白与多个起点 | `openings` + 对应 `initial_state` | 开场文字和初始进展是否一致 |
| 世界书资料 | `lorebook.entries` + `load` | 实际触发逻辑，不能只照搬原开关或深度字段 |
| 当前银币、好感、任务 | 通常为 message 状态 | 类型、初值、更新依据和完整数组/对象替换 |
| 本局难度、建角答案 | 通常为 session 状态 | 是否只影响当前局；中途改选会不会误重置剧情 |
| 确需多局共享的设置 | global 状态 | 是否真的应让同一世界全部会话共享 |
| 正则美化或文本标记 | `message_render` 与消息组件 | 只改变显示，还是原脚本还修改了事实 |
| 状态栏、地图、建角按钮 | Stage 中的 React 组件 + SDK | 显示与写入的同一数据来源、保存失败反馈 |
| 介绍页与开局预览 | 作者预览组件 | 预览没有会话身份，不能承担会话写入 |
| 原预设、宏、插件能力 | SR 预设 / 已有能力 / 非等价项记录 | 保留创作意图，逐项确认可替代性 |

不要承诺“所有酒馆插件原样兼容”。例如原脚本直接修改世界书、操控父页面或依赖某个扩展全局对象，不能仅换个文件后缀就运行；需要找到等价 SDK 能力，或把缺口写入迁移报告。

## 3. 先做内容等价的版本

优先完成角色、开局和世界资料，让作品可以用官方界面游玩。暂时保留原文，避免在迁移时顺手改写人物、删去线路或强化自己偏好的玩法。

对每条资料记录以下结果之一：

- **直接保留**：只是结构或字段变化。
- **拆分/合并**：内容进入多个对象，给出目标 ID。
- **用 SR 能力重建**：例如变量脚本改为状态定义 + SDK 按钮。
- **暂不支持或缺少资料**：写明玩家会缺少什么行为，保留原始来源供后续处理。

不要用“迁移完成”掩盖未读取的外部脚本、丢失的图片或无法恢复的条件逻辑。

## 4. 处理变量与更新语义

SR 角色 prompt / 世界书支持精确的 `{{user}}` 和已加载状态路径。前者是选中角色定义的名称；若作品允许玩家另取姓名，就把本局姓名放在合适状态域，并引用那个字段。

检查同一事实是否存在多份：角色提示词写死旧年龄、世界书重复旧地点、组件显示另一个变量，都会让故事互相矛盾。把可变化事实收敛到一份当前状态，再让文字和界面读取它。

当前模型更新只写激活的 message 根；global/session 不由主叙事自动更新。原系统里的增量、数组 push/remove、带数组下标路径，必须转换成 SR 接受的当前值替换方式。不要原样移植不兼容的 JSON Patch 或更新标签。见[状态与规则](state-and-rules.md)。

## 5. 再还原交互与素材

一个按钮要逐项确认：

1. 点击前显示的是什么？
2. 点击后只是切换界面、填入行动草稿，还是写入持久状态？
3. 下一轮模型应该看到哪些变化？
4. 写入失败、生成中或页面关闭时应该怎样反馈？

浏览地图通常只改变局部选中项，不应自动把角色传送过去。选择建角背景可以改变 session 资料，不能顺带重置已经游玩后的银币与年龄。主界面输入区由平台管理，舞台通过 SDK 填草稿或声明按钮。

将可以分发的素材整理到 assets；保留作者与授权说明。遇到无权限分发或失效的素材，记录缺口或使用得到许可的替代内容，不把“下载不到”当成静默删去的理由。

## 6. 验收原玩法

除了[常规打包检查](packaging.md)，至少对照三个原作场景：

| 场景 | 验收问题 |
| --- | --- |
| 两个开局 / 两种玩家选择 | 初始事实是否不同，另一分支材料是否被意外加载 |
| 一次真实状态变化 | 正文、面板、下一轮材料是否使用同一新值 |
| 一次只有浏览的操作 | 是否没有发消息、扣款或改动持久状态 |

条件触发要同时验证“应出现”和“不应出现”。如果原卡有大量资料，保留逐条映射表，未映射项数量应能解释。

## 交付物

交付可编辑源码、SR JSON / ZIP、原内容到新结构的映射、非等价项、素材来源和试玩步骤。明确写出哪些检查已经执行、哪些需要模型或浏览器继续验证。静态校验通过只说明结构与资源等检查通过，不代表原剧情完全等价。

想直接让 Agent 开始，使用[迁移请求示例](agent-authoring.md#迁移已有作品)。
