# 预设与模型

世界卡决定“这个世界有什么”；预设决定“怎样组织材料与叙事”；模型配置决定“请求发给谁”。把它们分清，作品就能在玩家自己的模型配置下运行，而不需要把作者的密钥或本地配置 ID 放进卡包。

## 从标准叙事开始

首次启动会安装「标准叙事」。它是文字世界的起点，包含人物、世界书、历史、状态更新与行动建议所需节点。权威文件是[初始化预设](../../initial-data/presets/标准叙事.json)，不另外维护一份供复制的旧默认 JSON。

先用它验证世界内容。需要改变语气时，再创建自己的预设或调整节点。先备份原预设，方便恢复；恢复某节点默认内容会替换该节点的自定义文字。

| 你想改变什么 | 优先改哪里 |
| --- | --- |
| 林舟的身世、习惯和知情边界 | 世界卡角色 prompt |
| 灯塔规矩和任务背景 | 世界书 |
| 当前银币和已知线索 | 状态定义及更新规则 |
| 整体采用简短对白、慢节奏描写 | 预设 main / 自定义风格节点 |
| 服务地址、API Key、可用模型 | 模型配置 |
| 温度、top-p、思考开关等请求偏好 | 预设模型参数；实际支持取决于模型路线 |
| 历史保留与摘要策略 | 预设上下文设置 |

不要用一句“这个模型支持”替代连通性和实际请求验证。配置保存成功也不等于账户额度、模型权限或所有参数都可用。

## 提示词编排

预设是一层节点列表。内置系统节点保持既定相对顺序；自定义文字节点可以插入其间。自定义节点选择明确的消息角色，填写内容并开启。内置节点的类型/角色受平台约束。

主提示词负责叙事要求，例如：

~~~text
用清楚、具体的动作和对白推进场景。尊重玩家对自身角色重要行动和对白的决定权。
人物只依据亲历、被告知或已经确认的事实行动。保留未知信息，避免提前揭露答案。
~~~

这段可以合并到适当节点，不应替换掉用于装入人物、历史、用户输入的必要变量。世界状态与行动建议节点各自控制对应能力；关闭其中一个不应被理解成关闭另一项。

## 可用变量

以下是此版本预设的固定聚合变量。通过编辑器插入变量时，以当前界面给出的列表为准。

| 变量 | 内容 |
| --- | --- |
| `{{user}}` | 选中的玩家身份名称 |
| `{{persona.prompt}}` | 玩家角色材料 |
| `{{characters.prompts}}` | 已激活的其他人物材料 |
| `{{world.lore}}` | 已激活的世界书正文 |
| `{{history.summary}}` | 当前使用的摘要 |
| `{{history.messages}}` | 保留历史消息，以原生消息角色加入 |
| `{{input.text}}` | 本轮用户输入 |
| `{{state.global}}` | 已加载的全局状态，只读背景 |
| `{{state.session}}` | 已加载的本局状态，只读背景 |
| `{{state.message}}` | 已加载的消息状态及规则，可供模型更新 |

`history.messages` 必须且只能在历史节点出现一次，`input.text` 必须且只能在输入节点出现一次。后处理节点不要重复插入输入、历史或摘要。未知变量、无效角色或内置节点顺序会导致保存校验失败。

角色/世界书里的 `{{state.message.coins}}` 是作者字段变量，不等同于预设整域变量。不要把两套规则互相套用；详见[世界内容变量](world-content.md#变量不要复制酒馆宏后就假定会展开)。

## 状态更新与行动建议

主叙事一次请求可以同时产生正文、状态更新和行动建议，平台把结构块与可见故事分离。状态失败不会自动让有效正文或另一项建议失效；停止或模型中断时，已显示正文可能保留，后处理不因此保证执行。

需要检查模型输出时，当前状态块使用 **JSONL**，每个非空物理行一个完整对象：

~~~text
<state_update>
{"path":"coins","value":10,"reason":"正文确认购买船票花费两枚银币"}
{"path":"clues","value":["信封上的灯塔印记"]}
</state_update>
<action_suggestions>
["向林舟询问信封印记。","沿码头寻找旧航线的线索。"]
</action_suggestions>
~~~

这是协议示意，不是每轮都要复制的固定结果。状态块没有外围数组，一项更新不能跨行；`path` 不含 scope 前缀。数组字段的值仍是完整 JSON 数组。行动建议自身使用字符串数组，点击建议会填入草稿，玩家确认发送后才构成行动。

行动建议与“独立 AI 帮答”是不同功能。这里讲的是主叙事结果中的建议，不能据此认为已经存在独立模型帮答流程。精确处理规则见[叙事协议](../runtime/server-narrative.md#叙事后处理与能力结果)。

## 上下文与长篇游玩

滚动摘要将较早历史整理为摘要，滑动窗口裁去超出窗口的旧历史。两者都受模型和预设的上下文预算限制，不能保证无限完整记忆。

创作者可以通过精简常驻材料、按关键词/状态加载资料、把当前事实保存为状态来减少噪声。不要把整部设定集和所有未来情节都常驻。若出现容量错误，查看[排错](troubleshooting.md)，先辨认是固定材料太大还是历史太长。

## 分享预设时

世界 ZIP 不包含模型 Key，也不包含你的会话历史。需要特定叙事风格时，可以另外分享导出的预设 JSON，并说明作品需要开启哪些节点；不要要求接收者使用你环境里的模型或预设 ID。写清推荐的风格、必要协议和已测试配置，比只写“必须某模型”更便于复现。
