# 组织世界内容

把作品拆成玩家身份、其他人物、开局和世界资料，模型就能在合适的时候获得合适的内容。本章中的片段应合并到已有 `world.json`，完整可运行版本见[最小示例](../../examples/worlds/minimal/world.json)与[雾港来信](../../examples/worlds/fog-harbor/world.json)。

## 角色：区分玩家身份与其他人物

`data.characters` 同时容纳玩家可扮演身份和世界中的其他人物。至少一项需要 `player_selectable: true`。同一世界可以有多种可选身份，创建会话时选择其中一种。

~~~json
{
  "id": "keeper",
  "name": "林舟",
  "presentation": {"type": "markdown", "text": "守灯人，熟悉雾港的航道。"},
  "content": "林舟守护旧灯塔多年，说话简短。他认识信封上的旧印记，但不会在初次见面时直接说明全部来历。",
  "player_selectable": false,
  "load": {"mode": "on_mention", "keywords": ["林舟", "灯塔"]}
}
~~~

`presentation` 面向玩家展示；`content` 用于模型演绎。身份、经历、说话习惯和知情范围写在 content 中；会随剧情变化的银币、位置、关系进度写入状态。角色 `id` 应稳定，`name` 可以是中文。`order` 控制角色材料的排序；不指定时为 0，同值保留原数组顺序。

选中角色的 content 进入玩家身份材料，其他已激活角色进入人物材料。不要把所有角色都写成“你”，否则玩家和模型角色容易混淆。玩家身份也会经过自己的 `load` 条件；初次制作时让它常驻，避免把必要身份意外隐藏。

角色介绍也可以使用 `{type: "component", component: "CharacterIntroduction"}`，引用已登记组件。没有 presentation 时不自动展示 content；介绍可能省略角色设定中的秘密。状态和立绘的 description 仍是纯文本语义说明。

## 世界书：按事实组织条目

`data.lorebook.entries` 放共享背景、地点、规则和按需出现的细节。每条有唯一 `id` 和非空 `content`，`title` 用于管理与阅读。

~~~json
{
  "id": "lighthouse-custom",
  "title": "灯塔的规矩",
  "content": "旧灯塔入夜后只接待持信的访客。守灯人需要先核对信封印记，才会谈起旧日航线。",
  "enabled": true,
  "load": {
    "mode": "on_mention",
    "keywords": ["灯塔", "林舟"],
    "keyword_logic": "any",
    "order": 10
  }
}
~~~

把“灯塔如何运作”和“玩家已经到达灯塔”分开。前者是世界设定，后者是剧情事实。条目进入上下文不代表事件已经发生，也不代表所有人物都知道它。

### 加载条件怎么选

| 写法 | 实际作用 | 适用内容 |
| --- | --- | --- |
| 不写 `load` 或 `mode: "always"` | 默认加入材料；仍要通过 `when` | 核心世界规则、主角身份 |
| `mode: "on_mention"` | 命中关键词后加入材料；必须提供非空 keywords | 地点、配角、专业知识 |
| `mode: "never"` | 不加入模型材料 | 只供组件/条件读取的控制信息 |
| `when` | 读取状态判断是否启用，可与前两类组合 | 已选择路线、特定任务阶段 |
| 世界书 `enabled: false` | 关闭该条目 | 暂停使用的资料 |

关键词按字面、区分大小写匹配；`keyword_logic` 默认 `any`，`all` 要求所有关键词均匹配。命中 `exclude_keywords` 中任意词会排除该条目。当前扫描材料包含准备中的摘要、保留历史和本轮输入；不能把它当成“人物当前在场”的判定，过去提过的名字也可能命中。

条件示例：

~~~json
{
  "mode": "always",
  "when": "getState('quest', {scope: 'message'}) === '向林舟核对灯塔印记'"
}
~~~

`when` 是受限状态表达式，不是任意 JavaScript。它不会修改状态。条件可用哪些运算符见[格式参考](../reference/world-card.md#加载条件)。排错时先确认状态定义和当前值，再确认加载条件，而不是反复强化条目中的提示词。

## 开局：同时定义场景与起点

每张卡至少有一个开局。玩家可以从不同地点或进度开始，但仍使用同一份人物和世界书。

~~~json
{
  "id": "lantern",
  "name": "灯塔下的约定",
  "content": "你站在灯塔石阶下，信封上的印记在风灯照耀下逐渐清晰。林舟问：“你从哪里找到它的？”",
  "initial_state": {
    "clues": ["信封上的灯塔印记"],
    "quest": "向林舟核对灯塔印记"
  }
}
~~~

以上片段要求先在 message 状态中声明 `clues` 和 `quest`，例如[状态教程](state-and-rules.md)中的定义。开局覆盖以**完整根字段**为单位；没列出的根沿用定义的初值。对象根一旦覆盖，要给出希望保留的全部字段。

`content` 是保存到会话的第一条助手消息。精确的 `{{user}}` 会在创建时替换为选中身份的名称。开局可另用 `presentation: {type: "component", component: "OpeningPreview"}` 或 Markdown 展示对象指定详情预览；预览是给选卡阶段看的，不执行建角或启动会话。见[呈现与交互](presentation.md)。

## 变量：不要复制酒馆宏后就假定会展开

角色 content 和已加载世界书正文支持：

| 变量 | 示例结果 |
| --- | --- |
| `{{user}}` | 选中身份的名称，例如“旅人” |
| `{{state.message.coins}}` | 本轮可见的消息状态银币 |
| `{{state.session.profile.name}}` | 已定义且已加载的本局资料字段 |
| `{{state.global.weather}}` | 已定义且已加载的世界共享字段 |

对象、数组整体输出为 JSON；数字 0 不会消失；数组下标不支持。不存在、无效或本轮未加载的状态路径展开为空。未知自定义占位保留原文，替换结果不会再次递归展开。这些规则针对角色 content 和世界书正文，不代表所有卡片字段都支持模板。

预设使用另一组固定聚合变量，见[预设与模型](presets-and-models.md)。不要把 `{{char}}`、酒馆脚本宏或自创的 `{{weather.today}}` 当作 SR 已实现的变量。

## 正文模板：按状态改变角色段落

角色的固定经历可以一直保留，态度、身份阶段和行动限制则可以根据状态选择段落。把条件直接写进角色的 `content`，同一份人设就能随剧情变化；世界书的 `content` 使用相同写法，玩家选中的角色身份也适用。

### 先定义状态，再编写正文

下面是合并到世界卡 `data` 中的片段。它定义了一个名为 `keeper` 的 message 状态根；这个名称由作者选择，并不是根据角色 ID 自动创建的私有状态：

~~~json
{
  "state": {
    "schema_version": 2,
    "scopes": {
      "message": {
        "keeper": {
          "type": "json",
          "initial": {
            "affinity": 70,
            "injured": true,
            "mood": "紧张，但努力保持镇定"
          },
          "description": "林舟的当前关系、身体与情绪状态。",
          "rules": {
            "keeper.affinity": "根据本轮已发生的互动调整好感度；计划和建议不改变关系。",
            "keeper.injured": "只有实际受伤或完成治疗时改变。",
            "keeper.mood": "描述本轮结束时的情绪，不替角色编造新的经历。"
          }
        }
      }
    }
  }
}
~~~

将下面的文本放入林舟的 `characters[].content`。JSON 文件中它仍然是一个字符串，换行写成 `\n`：

~~~text
林舟守护旧灯塔多年，习惯先观察再行动。
他当前的情绪是：{{state.message.keeper.mood}}。

{% if getState('keeper.affinity', {scope: 'message'}) >= 80 %}
林舟十分亲近{{user}}，愿意主动谈起自己的顾虑。
{% elif getState('keeper.affinity', {scope: 'message'}) >= 60 %}
林舟已经信任{{user}}，愿意分享自己知道且适合透露的线索。
{% else %}
林舟对{{user}}保持戒心，谈及关键线索时会有所保留。
{% endif %}

{% if getState('keeper.injured', {scope: 'message'}) === true %}
林舟目前受伤，行动迟缓，会避免剧烈活动。
{% endif %}
~~~

以初值 70 和受伤状态为例，本轮会保留“已经信任”和“目前受伤”两段，填入当前情绪与玩家名称；“十分亲近”和“保持戒心”不会进入模型材料。好感度下降后，下一次构建上下文会重新选择分支，世界卡中的完整模板一直保留。

### 条件块的规则

| 写法 | 含义 |
| --- | --- |
| `{% if 条件 %}` | 开始一组分支 |
| `{% elif 条件 %}` | 前面的条件都为 false 时才检查这一项，可以有多项 |
| `{% else %}` | 前面都为 false 时使用，可省略 |
| `{% endif %}` | 结束本组分支 |

每组只选择第一个成立的分支；没有命中且没有 else 时，这组不输出内容。可以连续写多组，也可以嵌套。每份 content 最多嵌套 32 层，总计最多 256 个 if/elif 条件。

条件与 `load.when` 使用同一套只读表达式，结果必须是布尔值。建议显式写 `scope`，避免不同作用域中存在同名状态时读错值。条件块不执行赋值、循环或任意 JavaScript，也不支持直接粘贴 EJS 的 `<% ... %>`。

`load.when` 决定整份角色或世界书是否加载；正文条件块决定已经加载的材料中出现哪些段落。两者都读取本轮捕获的完整状态视图。状态根自身的 `load` 另外控制值是否能通过 `{{state.…}}` 插入，以及 message 根是否进入本轮模型更新范围。因此，某个隐藏状态仍可用于条件判断，但直接插值会为空。

### 渲染与排错

- 主叙事和 AI 帮答使用相同的作者正文渲染规则。每次构建只使用已捕获的状态，本轮回复结算的新值从下一次构建开始生效。
- 角色、玩家身份和世界书通过 load 后，仅当本次实际编译的预设节点引用 `{{characters.content}}`、`{{persona.content}}` 或 `{{world.lore}}` 时，才渲染对应正文。关闭或跳过的节点、未被引用的材料不会触发正文条件；启用的自定义节点也可以引用，不要求固定节点名称。同一候选上下文里，多次引用同一材料会复用结果。
- 运行时只求值需要判断的条件，只渲染选中的分支。状态字符串、玩家名称等替换结果不会再次执行模板，即使其中出现 `{% if … %}` 或 `{{state.…}}`。
- 导入和世界内容校验会检查所有条件块的配对与表达式语法，包括未命中分支；保留原始字符串，不读取运行状态，也不把未知的普通 `{{…}}` 占位符当作导入错误。
- 不存在的状态直接参与比较可能使条件求值失败。确实允许缺失时显式写默认值，例如 `(getState('keeper.affinity', {scope: 'message'}) ?? 0) >= 60`。求值错误会终止本次上下文准备，不会被当作 false 后进入 else。
- 导入错误指出源字段路径和模板行列；运行时可在服务端的 `context.failed` 诊断中查看源字段与从 1 开始的行、列。主叙事仍通过现有 `invalid_context` 停止原因报告准备失败。
- 未知的 `{% … %}` 指令、缺少 endif、重复 else 等会报语法错误。需要字面展示起始标记时写 `\{%`，渲染时只消耗紧邻标记的一个反斜杠；JSON 字符串中相应写成 `"\\{% ... %}"`。条件引号里的 `%}` 不会提前结束指令。

条件模板只适用于角色和世界书的 `content`。开局、presentation、预设节点、聊天历史和模型回复不执行这套条件语法；开局仍只在创建会话时替换精确的 `{{user}}`。

## 写完后怎么验证

1. 新建会话，核对选中身份与开局文字。
2. 提到一个非主角人物或地点，观察模型是否获得对应设定。
3. 改用另一开局，检查初始线索与任务是否变化；银币等未覆盖值应沿用初值。
4. 对互斥规则，分别建立两局测试。不要只检查应出现的内容，也要检查不应出现的另一条线路是否泄漏。
5. 对正文条件模板，检查阈值两侧及相等时的结果，例如好感度 59、60、80；再组合受伤/未受伤状态，核对独立条件块。主叙事和帮答都应使用对应的当前材料。
6. 执行 `pnpm world:check <创作目录>`，然后按[打包与分享](packaging.md)检查最终包。

加载诊断和模型请求的定位见[排错](troubleshooting.md)。程序能验证结构与表达式，人物是否自然、秘密是否泄漏仍需要实际阅读回复。
