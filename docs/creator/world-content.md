# 组织世界内容

把作品拆成玩家身份、其他人物、开局和世界资料，模型就能在合适的时候获得合适的内容。本章中的片段应合并到已有 `world.json`，完整可运行版本见[最小示例](../../examples/worlds/minimal/world.json)与[雾港来信](../../examples/worlds/fog-harbor/world.json)。

## 角色：区分玩家身份与其他人物

`data.characters` 同时容纳玩家可扮演身份和世界中的其他人物。至少一项需要 `player_selectable: true`。同一世界可以有多种可选身份，创建会话时选择其中一种。

~~~json
{
  "id": "keeper",
  "name": "林舟",
  "description": "守灯人，熟悉雾港的航道。",
  "prompt": "林舟守护旧灯塔多年，说话简短。他认识信封上的旧印记，但不会在初次见面时直接说明全部来历。",
  "player_selectable": false,
  "load": {"mode": "on_mention", "keywords": ["林舟", "灯塔"]}
}
~~~

`description` 面向玩家展示；`prompt` 用于模型演绎。身份、经历、说话习惯和知情范围写在 prompt 中；会随剧情变化的银币、位置、关系进度写入状态。角色 `id` 应稳定，`name` 可以是中文。`order` 控制角色材料的排序；不指定时为 0，同值保留原数组顺序。

选中角色的 prompt 进入玩家身份材料，其他已激活角色进入人物材料。不要把所有角色都写成“你”，否则玩家和模型角色容易混淆。玩家身份也会经过自己的 `load` 条件；初次制作时让它常驻，避免把必要身份意外隐藏。

## 世界书：按事实组织条目

`data.lorebook.entries` 放共享背景、地点、规则和按需出现的细节。每条有唯一 `id` 和非空 `content`，`title` 用于管理与阅读。

~~~json
{
  "id": "lighthouse-custom",
  "title": "灯塔的规矩",
  "content": "旧灯塔入夜后只接待持信的访客。守灯人需要先核对信封印记，才会谈起旧日航线。",
  "enabled": true,
  "load": {
    "mode": "on_mention",
    "keywords": ["灯塔", "林舟"],
    "keyword_logic": "any",
    "order": 10
  }
}
~~~

把“灯塔如何运作”和“玩家已经到达灯塔”分开。前者是世界设定，后者是剧情事实。条目进入上下文不代表事件已经发生，也不代表所有人物都知道它。

### 加载条件怎么选

| 写法 | 实际作用 | 适用内容 |
| --- | --- | --- |
| 不写 `load` 或 `mode: "always"` | 默认加入材料；仍要通过 `when` | 核心世界规则、主角身份 |
| `mode: "on_mention"` | 命中关键词后加入材料；必须提供非空 keywords | 地点、配角、专业知识 |
| `mode: "never"` | 不加入模型材料 | 只供组件/条件读取的控制信息 |
| `when` | 读取状态判断是否启用，可与前两类组合 | 已选择路线、特定任务阶段 |
| 世界书 `enabled: false` | 关闭该条目 | 暂停使用的资料 |

关键词按字面、区分大小写匹配；`keyword_logic` 默认 `any`，`all` 要求所有关键词均匹配。命中 `exclude_keywords` 中任意词会排除该条目。当前扫描材料包含准备中的摘要、保留历史和本轮输入；不能把它当成“人物当前在场”的判定，过去提过的名字也可能命中。

条件示例：

~~~json
{
  "mode": "always",
  "when": "getState('quest', {scope: 'message'}) === '向林舟核对灯塔印记'"
}
~~~

`when` 是受限状态表达式，不是任意 JavaScript。它不会修改状态。条件可用哪些运算符见[格式参考](../reference/world-card.md#加载条件)。排错时先确认状态定义和当前值，再确认加载条件，而不是反复强化条目中的提示词。

## 开局：同时定义场景与起点

每张卡至少有一个开局。玩家可以从不同地点或进度开始，但仍使用同一份人物和世界书。

~~~json
{
  "id": "lantern",
  "name": "灯塔下的约定",
  "content": "你站在灯塔石阶下，信封上的印记在风灯照耀下逐渐清晰。林舟问：“你从哪里找到它的？”",
  "initial_state": {
    "clues": ["信封上的灯塔印记"],
    "quest": "向林舟核对灯塔印记"
  }
}
~~~

以上片段要求先在 message 状态中声明 `clues` 和 `quest`，例如[状态教程](state-and-rules.md)中的定义。开局覆盖以**完整根字段**为单位；没列出的根沿用定义的初值。对象根一旦覆盖，要给出希望保留的全部字段。

`content` 是保存到会话的第一条助手消息。精确的 `{{user}}` 会在创建时替换为选中身份的名称。开局可另用 `type: "component"` 和 `component` 指定详情预览；预览是给选卡阶段看的，不执行建角或启动会话。见[呈现与交互](presentation.md)。

## 变量：不要复制酒馆宏后就假定会展开

角色 prompt 和已加载世界书正文支持：

| 变量 | 示例结果 |
| --- | --- |
| `{{user}}` | 选中身份的名称，例如“旅人” |
| `{{state.message.coins}}` | 本轮可见的消息状态银币 |
| `{{state.session.profile.name}}` | 已定义且已加载的本局资料字段 |
| `{{state.global.weather}}` | 已定义且已加载的世界共享字段 |

对象、数组整体输出为 JSON；数字 0 不会消失；数组下标不支持。不存在、无效或本轮未加载的状态路径展开为空。未知自定义占位保留原文，替换结果不会再次递归展开。这些规则针对角色 prompt 和世界书正文，不代表所有卡片字段都支持模板。

预设使用另一组固定聚合变量，见[预设与模型](presets-and-models.md)。不要把 `{{char}}`、酒馆脚本宏或自创的 `{{weather.today}}` 当作 SR 已实现的变量。

## 写完后怎么验证

1. 新建会话，核对选中身份与开局文字。
2. 提到一个非主角人物或地点，观察模型是否获得对应设定。
3. 改用另一开局，检查初始线索与任务是否变化；银币等未覆盖值应沿用初值。
4. 对互斥规则，分别建立两局测试。不要只检查应出现的内容，也要检查不应出现的另一条线路是否泄漏。
5. 执行 `pnpm world:check <创作目录>`，然后按[打包与分享](packaging.md)检查最终包。

加载诊断和模型请求的定位见[排错](troubleshooting.md)。程序能验证结构与表达式，人物是否自然、秘密是否泄漏仍需要实际阅读回复。
