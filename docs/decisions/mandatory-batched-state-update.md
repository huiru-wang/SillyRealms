# One-request batched state update with prompt-level tool guidance

Status: historical decision. The [general tool-loop capability](agent-tool-loop.md) superseded the one-request/post-tool-stop and atomic-batch rules below. The [2026-11-11 narrative state-tail decision](narrative-state-tail-protocol.md), approved but pending implementation, now replaces narrative mandatory-tool rules and preset worldState/postHistory placement. The content below records the old design; it is not the target narrative contract. General tool code remains available. This historical decision superseded `conditional-state-review.md`.

## Behavior
- The preset `main` internal ID remains unchanged for existing presets, imports, exports, session references and world-book anchors. Its visible default name is **叙事风格**; new/default built-in prompt is empty and editable. The platform fixed system protocol is separate.
- The `worldState` context node emits a structured `【状态更新判断】` decision checklist **only when activated writable message fields exist**, immediately followed by `【可更新状态】` (definitions and current values). Activated global/session state is listed separately as `【只读状态】`.
- A generation with active writable message state sends **one** `update_state` tool and `toolChoice: required` (or the provider's equivalent `any`). The model is told to generate narrative first, then make exactly one `update_state({updates:[{path,value},...]})` call; no-change is `updates:[]`. No separate `review_state` request exists.
- The narrative ordering, exactly-once tool call, and post-tool silence are **prompt instructions only**. The runtime does not fail a Run for missing, repeated or out-of-order tool calls. It executes each returned tool call through the shared executor and persists individual `toolResult` entries without a special follow-up/review request.
- Tool execution failures do **not** fail the narrative Run. Each failed result is persisted and published as `tool.failed` over the session SSE with `{runId,toolCallId,toolName,code}`; the first-party Web Host currently ignores this event. No tool call means no state update, not an error.
- All updates are validated using the existing state domain in an isolated candidate snapshot; invalid updates, duplicate paths and more than 100 updates reject that entire **tool-call batch**. Valid preceding or subsequent tool calls can still succeed. The authoritative state changes only on a successful Run commit.
- If there is **no** activated writable message state, no tool is supplied or required and generation remains one ordinary narrative call. Summarization/compaction is a separate mechanism and may still make requests as needed.

## Compatibility and limits
- Legacy existing prompts are never overwritten if customized. The built-in default preset's *exact* previous main/postHistory text is safely cleared on DB open, and its old default node labels are updated. Imported legacy `main` nodes with generic labels are displayed/exported as `叙事风格`; their authored prompt content is preserved.
- `update_state` tool arguments changed from a single `{path,value}` to `{updates:[{path,value}]}`; old entries and tool calls in history are stored verbatim and not rewritten. Creator-facing SRStateAPI and HTTP state update APIs remain unchanged.
- The player **内心** composer control and its platform input protocol are removed. The parser continues to recognize historical blockquotes for existing conversation display; old drafts are projected as ordinary text rather than a typed mind block.
- Forced tool-choice does **not** guarantee prose before tools or even a tool call. When the provider API supports it, `toolChoice: required` (or equivalent `any`) remains enabled for writable state; otherwise no tool choice is forced. Missing calls and model output order are not runtime errors. Model-specific offline/real-provider tests are recommended before relying on this for high-value sessions. No paid provider calls were used for implementation tests.
- Only model/service, persistence or final state-commit failures affect the Run outcome. The tool failure event is best-effort SSE, with no replay guarantee or automatic compensation, and the regular creator-facing SDK contract remains unchanged.
