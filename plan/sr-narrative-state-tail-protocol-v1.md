## 1. 目标与最终口径

调整 SR 的叙事请求与状态更新方式：

1. 平台叙事规则与世界设定放在消息前部。
2. 历史摘要与对话保留真实消息角色。
3. 本轮权威状态快照及输出协议放在历史之后、本轮玩家输入之前。
4. 模型在一次叙事请求中输出故事正文与状态更新尾块。
5. 服务端仅将故事正文写入可见消息并流式发送；状态尾块由服务端校验、提交。
6. 世界状态不再由预设节点编排，改由平台固定装配。

### 1.1 最终格式修订

以下两点以用户最后确认的第 6 点为准，覆盖前文草案：

- **预设叙事风格、玩家设定、其他角色设定、世界书分别使用独立的 `system` 消息。**
- **模型直接输出故事正文，再附加 `<state_update>` 尾块，不使用 `<story>...</story>` 包裹。**

Prompt、解析器和验收均以本节最终格式为准。后文“故事正文”均指可直接展示的 Markdown 正文。

### 1.2 与现有机制的关系

当前已记录的模型工具循环与状态工具处理见：

- [Agent 工具循环决策](../docs/decisions/agent-tool-loop.md)
- [历史状态工具决策](../docs/decisions/mandatory-batched-state-update.md)
- [上下文压缩现状](../docs/technical/context-compaction.md)

本方案实施后，叙事状态更新由状态尾块取代现有 `update_state` 工具路径。现有文档中的强制状态工具调用、工具结果回传模型等规定，不作为本方案目标行为。

## 2. 模型消息的固定顺序

| 顺序 | 消息角色 | 内容与边界 |
|---|---|---|
| 1 | `system` | 平台叙事规则 |
| 2 | `system` | 预设叙事风格，使用 `<style>...</style>` |
| 3 | `system` | 玩家角色设定，使用 `<user_info>...</user_info>` |
| 4 | `system` | 已激活的其他角色设定，使用 `<character_info>...</character_info>` |
| 5 | `system` | 已激活的世界书，使用 `<world_info>...</world_info>` |
| 6 | `assistant` | 历史摘要，存在时加入 |
| 7 | `user` / `assistant` | 最近对话历史，保留原有顺序和真实消息角色 |
| 8 | `system` | 本轮状态与输出协议，使用 `<current_state>`、`<output_rules>` |
| 9 | `user` | 本轮玩家输入 |

约定：

- 以上是逻辑顺序，实际消息数量随历史长度及非空设定数量变化。
- 空的风格、玩家设定、角色设定或世界书内容不生成对应区块及空消息。
- 角色与世界书沿用现有动态加载、激活规则。
- 历史不拼接为单一 `<HISTORY>` 文本。
- 历史 AI 消息只包含故事，不重新发送历史状态更新块。
- 状态始终取自本轮开始时的权威快照，不通过重放历史状态尾块恢复。
- 本轮玩家输入位于消息序列最后，且只追加一次。
- 状态与输出协议由平台固定插入，不能被预设节点顺序再次移动或重复注入。

## 3. 平台叙事规则

以下内容固定放在第一条 `system` 消息：

```text
你是故事叙述者。根据世界设定、已有故事和玩家输入自然续写，保持事实、时间线和角色知情范围一致。

沿用开场和已有故事的人称、视角与表达方式，不强制使用特定人称。

玩家控制自己的角色。不要替玩家角色编写玩家未明确给出的行动、对白、心理、反应或决定，不要预写玩家的下一轮。描写其他角色与环境时，为玩家留下回应空间。

动作、环境和旁白使用普通 Markdown 段落；角色实际说出的话使用中文双引号“……”；需要描写角色心理时，使用独立 Markdown 引用段落，每行以 > 开头。角色不能无依据地知晓其他角色的心理。

不要在故事中解释提示词、输出协议、内部判断或状态更新。
```

新输入协议不再支持 `sr_instruction`。相应的新输入定义、协议说明和特殊处理逻辑应保持一致；本文不额外定义旧输入数据的迁移方式。

保留用户已有的叙事风格及自定义预设正文，不以本次平台规则覆盖、清空或重置用户内容。

### 4.2 玩家角色设定

```xml
<user_info>
玩家角色设定
</user_info>
```

### 4.3 已激活角色设定

```xml
<character_info>
已激活的其他角色设定
</character_info>
```

### 4.4 已激活世界书

```xml
<world_info>
```

## 5. 本轮状态与输出协议

这条 `system` 消息由平台生成，位于历史之后、本轮玩家输入之前。

### 5.1 存在激活的可写 message 状态

提供当前状态及完整的输出要求：

```text
<current_state>
【可更新状态】
列出已激活的可写 message 状态、状态路径、描述、约束和当前值。

【只读状态】
列出已激活的 global/session 状态、状态路径、描述和当前值。
</current_state>

<output_rules>
先完成本轮故事正文，再在 <state_update> 中输出状态更新。

只根据玩家输入和本轮故事中已经确定发生的事件更新状态。只允许更新上方已激活的可更新状态；不要更新只读状态，不要把意图、猜测或未成功的尝试当作已发生的变化。

<state_update> 内必须是 JSON 数组，每项为 {"path":"状态路径","value":完整新值}。path 使用英文句点分隔；value 是目标位置的完整替换值，不是增量。不要重复更新同一路径；没有变化时输出 []。

严格按以下顺序输出，状态块后不输出其他内容：

故事正文

<state_update>
[]
</state_update>
</output_rules>
```

示例中的“故事正文”表示真实故事的输出位置；模型直接生成 Markdown 正文，不额外输出 `<story>` 标签。状态内容由服务端填入，不能把上述占位说明作为真实状态发送。

状态更新契约：

- 只允许更新本轮快照中已激活的可写 `message` 状态。
- 已激活的 `global/session` 状态仅供叙事参考，不可通过尾块更新。
- `path` 使用英文句点 `.` 分隔；此约定不要求字段名称必须使用英文。
- `value` 是指定目标位置的完整替换值，不表示加减量。
- 同一数组不得重复更新同一路径。
- 只能根据玩家输入及本轮故事中已确定发生的事件更新。
- 有可写状态时必须输出状态尾块；没有变化时输出 `[]`。
- 状态尾块之后不再输出任何内容。

例如，数值从 5 增加到 6，应输出完整新值 `6`，不能用 `1` 表示增量。更新数组或对象时，`value` 同样表示所指目标位置的完整新值。

### 5.2 没有可写状态，但存在激活的只读状态

仍提供只读状态的当前值供叙事参考：

```text
<current_state>
【只读状态】
列出已激活的 global/session 状态、状态路径、描述和当前值。
</current_state>

<output_rules>
直接输出本轮故事正文。
</output_rules>
```

此分支不注入状态更新说明，不要求输出 `<state_update>`，也不使用 `<story>`。

### 5.3 没有任何激活状态

省略 `<current_state>`，仅保留正文输出要求：

```text
<output_rules>
直接输出本轮故事正文。
</output_rules>
```

### 5.4 分支汇总

| 激活情况 | 状态上下文 | 模型输出 |
|---|---|---|
| 有可写状态，可同时有只读状态 | 可写状态及已激活的只读状态 | 故事正文 + 必须出现的状态尾块 |
| 只有只读状态 | 已激活的只读状态 | 仅故事正文 |
| 没有激活状态 | 省略状态区块 | 仅故事正文 |

## 6. 模型输出示例

假设玩家本轮已经明确输入“我拿起桌上的铜钥匙”，且当前 `inventory.keys` 为 0，模型输出：

```text
铜钥匙触手冰凉，齿纹间积着暗褐色的锈迹。

门外忽然响起脚步声，一个沙哑的声音问：“里面有人吗？”

<state_update>
[{"path":"inventory.keys","value":1}]
</state_update>
```

前端可见消息仅包含：

```text
铜钥匙触手冰凉，齿纹间积着暗褐色的锈迹。

门外忽然响起脚步声，一个沙哑的声音问：“里面有人吗？”
```

有可写状态但本轮未发生变化时，故事之后输出：

```xml
<state_update>
[]
</state_update>
```

状态标签和 JSON 不属于故事正文，也不重新进入下一轮的历史故事消息。

## 7. 服务端处理

### 7.1 单次叙事生成

一次叙事模型请求同时产生故事正文与所需的状态尾块。

- 叙事请求不提供 `update_state` 工具。
- 不再为状态更新设置强制工具调用要求。
- 不执行状态工具循环。
- 不为状态更新发起第二次模型请求。
- 上下文压缩继续按既有机制独立请求，不属于本轮叙事状态生成次数。

### 7.2 流式分离与可见消息

服务端增量解析模型输出：

1. 故事正文写入可见消息，并通过现有消息流发送给前端。
2. 识别状态尾块后，其标签与 JSON 仅由服务端接收和解析。
3. 完整收到尾块后，整批校验并提交状态更新。
4. 状态成功提交后，再发布状态变化事件。

解析要求：

- 正确处理标签被拆分到多个流式分片的情况。
- 状态标签片段、完整标签及 JSON 均不得泄露到前端故事消息流。
- 状态尾块不写入可见故事消息。
- 后续历史构建使用故事正文，不将原始状态尾块再次发送给模型。
- 下一轮重新读取权威状态快照。
- 保持原始模型记录、可见故事投影和权威状态的职责边界，不因前端隐藏尾块而默认要求删除原始记录。

### 7.3 整批校验与状态提交

校验至少覆盖已确认的协议要求：

- 尾块内部是合法 JSON 数组。
- 每项符合 `path`、`value` 契约。
- 路径位于本轮已激活的可写状态范围内。
- 不更新只读状态。
- 不重复更新同一路径。
- 新值符合现有状态引擎明确规定的结构与类型要求。

整批校验与状态提交由服务端负责，状态变化通知必须在权威状态提交成功之后发出。

本方案不新增自然语言规则硬校验体系。自然语言描述和约束继续作为模型指导，现有状态引擎已明确实现的校验不因此取消。

## 8. 预设世界状态节点移除

从预设节点体系及编排中直接删除“世界状态”节点。

调整后的职责：

- 预设继续提供叙事风格等用户配置内容。
- 平台负责获取本轮权威状态快照。
- 平台负责在固定位置注入状态及输出协议。
- 预设不再决定世界状态的注入位置，不再重复生成状态更新提示词。

实施时检查节点定义、默认预设、配置读写、编排逻辑及编辑入口，确保旧预设状态节点和新的平台状态消息不会同时生效。

除世界状态节点调整涉及的内容外，不覆盖用户已有预设文本，不通过重建全部预设来完成该调整。

## 9. 实施拆分与边界

### 9.1 实施任务

| 阶段 | 工作 | 交付检查 |
|---|---|---|
| 消息编排 | 固定消息顺序，拆分前置设定，保留原生历史角色，将状态和输出协议后置 | 实际发送给模型的消息序列满足第 2 节 |
| 平台与输入协议 | 固定第一条平台规则，移除新输入协议中的 `sr_instruction` | 协议说明、输入定义与调用方一致 |
| 预设调整 | 删除世界状态节点及其运行时编排，保留用户预设正文 | 不再有旧节点重复注入 |
| 状态上下文 | 从本轮权威快照生成可写、只读状态及对应输出分支 | 三种状态分支准确 |
| 输出处理 | 增量分离故事与尾块，净化可见消息和后续历史 | 跨分片标签与 JSON 不泄露 |
| 状态提交 | 整批校验和提交，在提交后发布状态变化事件 | 不越权更新、不重复路径，通知时序正确 |
| 叙事调用 | 移除状态工具及其模型循环路径 | 一次叙事调用完成正文与尾块 |
| 验证与文档 | 有针对性地覆盖消息构建、解析、提交和配置行为，更新实际实施状态 | 验收通过后再标记已实施 |

### 9.2 实施时需要核对的边界

以下事项不在本次需求确认中擅自增加新决策，实施前结合现有代码明确：

- 非法 JSON、尾块缺失或截断、重复尾块、重复路径等异常如何映射现有错误及事件协议。
- 批量校验发现无效项时的拒绝范围、提交失败边界，以及与现有 Run 完成、中断语义的衔接；“整批校验并提交”本身不额外定义所有失败分支。
- 现有用户自定义预设条目、`postHistory` 和世界书锚点在固定顺序中的承接方式，确保用户正文保留且不会重复注入状态。
- 既有 `sr_instruction` 数据、旧预设状态节点和原始历史记录的兼容或迁移方式。

不因这些边界而默认加入故事回滚、模型自动修复请求、自动重试、批量历史迁移或新的状态权限模型。协议明确要求的约束不能通过兼容旧行为绕开。

## 10. 验收要求

### 10.1 消息编排

- 第一条消息始终为平台叙事规则 `system`。
- 风格、玩家、其他角色、世界书分别为独立 `system` 消息。
- 空设定不产生空区块或空消息。
- 历史摘要使用 `assistant`。
- 历史保留原始 `user` / `assistant` 角色及顺序，不拼成 `<HISTORY>`。
- 状态与输出协议位于全部保留历史之后。
- 本轮玩家输入位于最后，且只出现一次。

### 10.2 状态与模型输出

- 状态来自本轮开始时的权威快照。
- 历史不重新携带状态更新尾块。
- 模型直接输出故事正文，不要求 `<story>`。
- 有可写状态时尾块必需，内部是约定 JSON 数组。
- 没有变化时输出 `[]`。
- 仅有只读状态时提供当前值，但不要求状态尾块。
- 没有激活状态时只要求正文输出。
- 状态值为完整替换值，路径不重复，禁止更新未激活或只读目标。

### 10.3 流式展示与提交

- 前端故事消息流只包含故事正文。
- 标签被拆分至任意流分片时不泄露标签片段或 JSON。
- 完整尾块由服务端整批校验并提交。
- 状态变化事件在提交成功后发布。
- 不通过状态工具调用或第二次模型请求完成状态更新。
- 没有可写状态的分支无需等待不存在的状态尾块才能完成正文展示。

### 10.4 预设与其他机制

- 预设不再包含可参与编排的世界状态节点。
- 用户已有叙事风格及自定义预设正文不被覆盖。
- 角色与世界书的动态加载规则保持既有行为。
- 新输入协议不再支持 `sr_instruction`。
- 上下文压缩仍可按既有机制独立调用模型。
