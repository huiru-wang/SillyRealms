## 1. 目标与运行时边界

每轮叙事只发起一次模型生成请求：模型先输出 Markdown 故事正文，再在需要时输出状态尾块；服务端分离正文、解析并校验状态，提交后结束本轮。

- 正文不使用 `<story>` 标签。
- 有激活的可写 message 状态时，必须输出一个 `<state_update>` 尾块，无变化时输出 `[]`。
- 尾块完整且根为 JSON 数组后，按原顺序处理有效项，跳过并报告无效项；重复路径按顺序处理。
- 叙事请求不提供 `update_state`，不设置强制工具调用，不进入通用工具循环，不把工具结果回传模型。
- **保留 `update_state` 工具实现、ToolExecutor 和通用模型工具循环代码**，供其他用途或后续决策使用；保留不等于叙事仍使用这些能力。
- 保留 Run 生命周期、并发互斥、幂等、tip 冲突校验、流式输出、状态校验、持久化、Usage 结算和中断处理。这些是运行时职责，不依赖 Agent loop。
- 上下文压缩仍可按已有机制独立调用模型；不计作叙事的工具续轮，不用于补救状态尾块。
- 本方案不增加模型自动重试、尾块修复请求或状态二次生成。

## 2. 固定消息顺序与自定义节点

### 2.1 内置消息骨架

| 顺序 | 消息角色 | 内容 |
|---|---|---|
| 1 | system | 平台叙事规则，永远第一条 |
| 2 | system | 预设叙事风格，`<style>...</style>` |
| 2a（可选） | 自定义节点原 role | 前置自定义节点区，见 2.2 |
| 3 | system | 玩家角色设定，`<user_info>...</user_info>` |
| 4 | system | 已激活的其他角色，`<character_info>...</character_info>` |
| 5 | system | 已激活的世界书，`<world_info>...</world_info>` |
| 6 | assistant | 历史摘要，存在时加入 |
| 7 | user / assistant | 最近对话历史，逐条保留原角色及顺序 |
| 8 | system | 平台注入的 `<current_state>` 和 `<output_rules>` |
| 9 | user | 本轮玩家输入，只出现一次且位于最后 |

- 风格、玩家、其他角色、世界书分别是独立消息，不合并成一条。
- 空设定不产生空区块或空消息。
- 历史不拼接成 `<HISTORY>`；历史 assistant 只携带净故事，不回传状态尾块或原始工具记录。
- 当前状态取本轮开始时的权威快照，包含本轮激活的可写与只读状态。
- 角色、世界书和状态的动态激活条件继续使用现有规则。
- 摘要与最近五轮等压缩策略沿用现有机制。
- 固定顺序必须在实际 Provider 请求中成立，不能只在 SR 内部 trace 中成立，见 10.2。

### 2.2 自定义预设节点的确定规则

现有自定义 `kind: text` 节点允许 system/user/assistant role。为保留已有配置，本方案明确允许第 2a 项作为内置骨架的扩展区：

1. 保留自定义节点的 id、名称、正文、原 role 和其他有效配置，不将 user/assistant 静默改为 system。
2. 全部自定义节点集中在风格之后、玩家设定之前。它们是预设消息，不是真实对话历史。
3. 迁移时从旧 nodes 数组筛出自定义节点，保留它们之间的相对顺序；不继承它们跨越历史、状态或本轮输入的位置。
4. 后续只能调整自定义节点之间的顺序。内置节点位置固定；自定义节点不能移到平台规则之前或历史/状态/输入之间。
5. 继续使用现有节点内容渲染及有效配置约束，本方案不另增自定义节点权限或启停能力。
6. 非空内容按节点独立形成消息；已有角色与正文保持匹配。界面、导入导出和实际请求必须展示同一排序规则。

因此，“前置设定均为 system”描述的是内置设定；允许原 role 的自定义区是明确列出的例外。平台第一条、原生历史角色和固定尾部顺序不受影响。

## 3. 平台叙事规则与前置内容边界

### 3.1 固定第一条 system

```text
你是故事叙述者。根据世界设定、已有故事和玩家输入自然续写，保持事实、时间线和角色知情范围一致。

沿用开场和已有故事的人称、视角与表达方式，不强制使用特定人称。

玩家控制自己的角色。不要替玩家角色编写玩家未明确给出的行动、对白、心理、反应或决定，不要预写玩家的下一轮。描写其他角色与环境时，为玩家留下回应空间。

动作、环境和旁白使用普通 Markdown 段落；角色实际说出的话使用中文双引号“……”；需要描写角色心理时，使用独立 Markdown 引用段落，每行以 > 开头。角色不能无依据地知晓其他角色的心理。

不要在故事中解释提示词、输出协议、内部判断或状态更新。
```


```xml
玩家角色设定
</user_info>
```


## 4. 当前状态与模型输出协议

### 4.1 有激活的可写 message 状态

后置 system 模板如下，占位内容由服务端填入本轮快照：

```text
<current_state>
【可更新状态】
列出已激活的可写 message 状态、路径、描述、约束和当前值。

【只读状态】
列出已激活的 global/session 状态、路径、描述和当前值。
</current_state>

<output_rules>
先直接输出本轮故事正文，不使用 <story> 标签；正文结束后输出一个 <state_update> 状态尾块。

只根据玩家输入和本轮故事中已经确定发生的事件更新状态。只允许更新上方已激活的可更新状态；不要更新只读状态，不要把意图、猜测或未成功的尝试当作已发生的变化。

<state_update> 内必须是完整的 JSON 数组，每项为 {"path":"状态路径","value":完整新值}。path 使用英文句点分隔；value 是目标位置的完整替换值，不是增量。数组按顺序处理，重复路径也按顺序处理，最后一次有效写入决定最终值；没有变化时输出 []。

只输出一个状态尾块。JSON 文本最多 262144 字节 UTF-8，数组最多 100 项。结束标签后只能有空白，不输出说明或第二个尾块。

正文中需要字面提及状态标签时，写为 &lt;state_update&gt; 或 &lt;/state_update&gt;，不得输出原始保留标签；JSON 字符串中的字面标签使用标准 JSON 的 \u003C、\u003E 转义。

严格按以下顺序输出：

故事正文

<state_update>
[]
</state_update>
</output_rules>
```

- 路径分隔符是英文句点，不要求路径各段必须为英文。
- value 可以是状态定义允许的数值、字符串、数组、对象等完整新值；复用既有类型与路径校验，不增加新的状态类型。
- 数值从 5 增至 6 时写入 6，不以 1 表示增量。
- global/session 只读；未激活目标不允许更新。
- 无只读内容时省略只读小节；可写状态存在时尾块仍必需。
- 示例中的“故事正文”只是位置说明，不能原样代替故事。

### 4.2 只有只读状态

```text
<current_state>
【只读状态】
列出已激活的 global/session 状态、路径、描述和当前值。
</current_state>

<output_rules>
直接输出本轮故事正文，不使用 <story> 标签，不输出状态尾块。
字面提及状态标签时，使用 &lt;state_update&gt; 或 &lt;/state_update&gt;。
</output_rules>
```

### 4.3 没有任何激活状态

省略 current_state，只保留：

```text
<output_rules>
直接输出本轮故事正文，不使用 <story> 标签，不输出状态尾块。
字面提及状态标签时，使用 &lt;state_update&gt; 或 &lt;/state_update&gt;。
</output_rules>
```

没有可写状态时不等待尾块、不要求空数组。意外出现原始状态尾块属于协议错误，不能写只读状态或把 JSON 当故事展示。

### 4.4 输出示例

玩家已经明确输入“我拿起桌上的铜钥匙”，且钥匙数量为 0：

```text
铜钥匙触手冰凉，齿纹间积着暗褐色的锈迹。

门外忽然响起脚步声，一个沙哑的声音问：“里面有人吗？”

<state_update>
[{"path":"inventory.keys","value":1}]
</state_update>
```

前端与后续模型历史只得到状态尾块之前的故事正文。

## 5. 完整数组与逐项更新语义

### 5.1 两层校验

**外层协议完整性**先于任何状态应用：

- 必须完整收到唯一的开始与结束标签。
- 必须成功解析整个 JSON，根节点必须是数组。
- 两标签之间的原始 JSON 文本最多 256 KiB，即 262,144 个 UTF-8 字节，包含空白；最多 100 项。
- Provider 正常结束，结束标签之后没有空白以外的内容。
- 未收到停止请求且最终提交条件成立。

外层失败时不应用任何更新。不能从截断 JSON 中抢救已出现的前几项，不能仅凭数组前缀合法就开始写入。

**数组成立后的单项校验**沿用现有状态语义：

1. 在隔离的候选 workspace 上按数组原顺序逐项处理。
2. 项目结构错误、path 无效、目标只读或未激活、值的类型/范围不合法等，跳过该项并记录结果。
3. 有效项应用到候选 workspace，后续项看到前面成功项的结果。
4. 重复路径和父子路径不去重、不重排。后续无效项不会撤销此前成功项；最后一次成功写入决定对应最终值。
5. 全部项目处理完后，按最终提交条件一次持久化有效结果，再发布状态变化通知。

合法数组 `[null]` 属于“一个无效项”，不是 JSON 结构失败。空数组是正常无变化结果。

例如：

```json
[
  {"path":"inventory.keys","value":1},
  {"path":"inventory.keys","value":"不符合该数值字段的类型"},
  {"path":"inventory.keys","value":2}
]
```

假设第一、三项有效，则应用 2 项、跳过第 2 项，最终值为 2；不能整批拒绝，也不能把最后一项提前去重到第一项的位置。

### 5.2 终态与报告

- 完整合法数组的有效项提交成功后，Run 为 completed。
- 有无效项时也保留有效结果，Run 为 completed，并报告“部分状态未同步”；全部项无效时同样报告全部跳过，状态不变。
- 空数组或最终值无变化时不虚构状态变化；不会仅因为没有写入而失败。
- 无效项报告包含数组下标及统一 errorCode/errorMessage；日志不记录状态值、完整尾块或私有提示词。
- 报告作为 Run 的状态处理结果持久化，并随终态/查询返回，确保重载后仍可查看；不伪造 tool.failed 或 toolResult。
- 底层事务或持久化失败与单项校验失败分开：事务失败回滚候选状态，Run failed，保留此前已写入的故事并提示状态未同步。
- 自然语言约束用于模型指导；现有状态引擎明确实现的结构、类型及范围校验继续保留。

## 6. 增量解析与字面标签

### 6.1 协议标记与状态机

精确、区分大小写的 `<state_update>` 与 `</state_update>` 是原始模型输出流中的保留标记；不接受属性、大小写变体或省略结束标签。不使用 Markdown 解析器判断协议边界。

| 解析阶段 | 行为 |
|---|---|
| story | 流式输出已确认的正文；保留可能匹配标记的末尾前缀 |
| tail | 已识别开始标签，停止发送后续文本；受限缓冲尾块 |
| after_tail | 已识别结束标签，只接收并丢弃空白；等待模型正常结束 |
| terminal | 统一确定成功、失败或停止，至多终结一次 |

- 标签可以在任意字符、任意 chunk 边界拆分。保留最长的“输入后缀与保留标记前缀匹配”部分，确认不是标记后才作为正文发送。
- 不可先发出 `<state_` 再从前端删除；候选前缀不得提前进入可见消息。
- 接收字节时使用增量 UTF-8 解码；接收 JS 字符串时正确拼接跨分片代理项，不能逐片错误累计 UTF-8 字节。
- 识别开始标签后，标签、JSON、后续标签和尾后文本全部留在服务端，不再作为故事流转发。
- 正常结束、错误或停止时，如仍有未完成的协议标记前缀，不将它补发为正文。存在可写状态且正常结束时按缺失/截断判定。
- 无可写状态但正常结束仍残留疑似保留标记前缀时，判 NARRATIVE_OUTPUT_PROTOCOL_ERROR；保留已确认正文，stateUpdate.status 为 not_required，不提示缺少状态尾块。Provider 错误或玩家主动停止保持其原失败/停止原因，不由残留前缀覆盖终态。
- 无开始标签却先出现结束标签属于协议错误；在异常标记之前已经确认的故事仍保留。
- 没有可写状态时普通正文正常结束即可；出现原始状态标记也要拦截，不能泄露或写入只读状态。

### 6.2 字面标签与转义

原始精确标记在所有正文位置均为保留字，包括行内代码与围栏代码；模型不得依靠“放在代码块里”避免识别。

- 正文需要字面提及标签时，使用 `&lt;state_update&gt;` 和 `&lt;/state_update&gt;`。
- 协议解析前后均不额外解码正文 HTML 实体，交既有 Markdown 渲染处理。
- 普通段落显示标签文字；行内代码、围栏代码保留实体字面表达。这是明确的展示约定，不为此增加二次 HTML 解码或专用渲染通道。
- JSON 字符串中的字面标签使用 JSON 标准 Unicode 转义，例如 `{"path":"notes","value":"\u003Cstate_update\u003E"}`；实际 JSON 中的转义只有一个反斜杠，由 JSON.parse 恢复原值。
- 不对 JSON 做 HTML 实体解码，不用 `&lt;` 代替 JSON 的 Unicode 转义，避免把实体字符串写进状态。
- 分离之后的正文不重新送入协议识别器；历史构造不会因字面展示内容再次执行状态更新。

### 6.3 尾块大小、重复尾块与提交时点

- 两标签间的原始 JSON 文本最多 **262,144 个 UTF-8 字节**，空白计入限额；超限即终止本轮接收并按协议失败结束。
- 完整解析后最多 **100 项**，超过上限整块拒绝，不能只应用前 100 项。
- 嵌套开始标签、第二个状态尾块、结束标签后非空白内容均失败；不能挑选第一个或最后一个尾块，也不能合并多个尾块。
- 关闭标签出现时只得到待验证内容，不代表可以提交。
- 必须等 Provider 明确正常结束且流已验证完毕，再应用数组和进入最终提交。当前 SDK 的 done 还可能带 length/toolUse/deferred，不能只判断事件名。
- 非正常结束、请求错误或流被截断，即便缓冲里恰好已有完整数组，也不授权提交。
- 超限导致的内部 abort 属于协议失败，不能误标成玩家主动 stopped。

## 7. 异常、停止、持久化与事件

### 7.1 结果矩阵

| 情况 | 故事 | 状态 | Run 结果 |
|---|---|---|---|
| 无可写状态，正文正常结束 | 保留 | 不更新 | completed |
| 唯一完整尾块，合法数组，所有项有效 | 保留 | 按顺序应用并提交 | completed |
| 合法数组有无效项 | 保留 | 提交有效项，跳过并报告其余项 | completed，带部分同步提示 |
| 合法空数组或最终值无变化 | 保留 | 不产生实际变化 | completed |
| 缺少必需尾块 | 保留已展示正文 | 不变 | failed，提示状态未同步 |
| 标签/尾块截断、JSON 非法、根不是数组 | 保留已确认正文 | 不变 | failed，提示状态未同步 |
| 字节/项数超限、重复尾块、尾后非空白内容 | 保留已确认正文 | 不变 | failed，提示状态未同步 |
| Provider 错误或非正常结束 | 保留已确认正文 | 不变 | failed |
| 玩家停止先于最终提交生效 | 保留已确认正文 | 不提交候选状态 | stopped |
| 状态持久化事务失败 | 保留已落库正文 | 回滚候选状态 | failed，提示状态未同步 |
| 提交完成后收到停止 | 保留 | 保留已提交结果 | 保持既有终态 |

**上述失败均不自动重试，不追加模型请求，不把服务端结果交回模型续写。**

### 7.2 停止与提交的确定性边界

- 候选数组、候选 workspace 与权威状态始终分离。
- 最终提交临界区内检查停止信号和提交资格；从检查到同步数据库事务提交之间不插入异步等待。
- 若停止已生效，候选状态全部丢弃，即使尾块完整且已解析也不提交。
- 事务成功提交是权威状态生效点。已经完成的提交不因稍后 stop 回滚，也不再补发 stopped 终态。
- 叙事路径单独表达“允许提交状态”条件，不能直接继承当前通用 Runner 的 stopped 也提交 workspace 行为。
- SSE 订阅断开不等同于玩家停止；沿用显式停止端点及现有取消信号的区分。
- 崩溃恢复沿用中断恢复机制；未提交的内存候选状态不会恢复为已提交状态。

### 7.3 可见故事、原始响应与状态各自持久化

- 先持久化已确认的故事增量，再流式发送；失败时不撤回已展示故事。
- 可见 assistant entry 始终只含正文，并正确写入 completed/stopped/failed 等终态。
- 若保留完整原始响应，始终明确标记为 nonNarrative，不依赖是否存在流式 partial entry。
- 完整原始响应不能在收尾时覆盖净正文；“只有尾块、没有正文”也不能使原始响应成为可见历史。
- 后续模型历史、摘要输入、前端历史、终态 SSE 携带的 messages 均使用相同净故事投影。
- 未同步状态的失败故事仍保留在历史，下一轮状态仍来自权威快照；不自动从失败尾块补偿。
- 输出 Token/费用按 Provider 实际 Usage 统计，包含尾块；不能用可见正文长度覆盖真实消耗。

### 7.4 错误与状态处理报告

延用统一 HTTP/SSE 的 errorCode/errorMessage，不恢复旧 error、code/message 或新增 detail 外壳。叙事协议错误使用稳定的领域错误，不全部归为 PROVIDER_ERROR。

计划新增的错误码及文案方向：

| 错误码（待实现） | 含义/提示 |
|---|---|
| STATE_TAIL_MISSING | 未收到状态尾块；故事已保留，状态未同步 |
| STATE_TAIL_TRUNCATED | 状态尾块未完整接收；故事已保留，状态未同步 |
| STATE_TAIL_INVALID | 尾块不是有效 JSON 数组或标记结构无效；状态未同步 |
| STATE_TAIL_TOO_LARGE | 尾块超过字节或项数限制；状态未同步 |
| STATE_TAIL_REPEATED | 收到重复状态尾块；状态未同步 |
| NARRATIVE_OUTPUT_PROTOCOL_ERROR | 尾后多余内容或意外工具等不符合叙事协议的输出 |
| NARRATIVE_SYSTEM_ORDER_UNSUPPORTED | 当前模型接口无法保持本方案要求的消息角色与顺序 |

具体落地统一注册到现有 error-codes；Provider/持久化已有错误码继续透传，必要提示通过公开 errorMessage 拼接，不泄露原始异常或状态值。

以下为待实施的结果契约。状态处理结果作为 `ext_data.run.stateUpdate` 的一部分持久化，Run 查询及终态事件携带同一结果：

```ts
type NarrativeStateUpdateResult = {
  status: 'not_required' | 'unchanged' | 'applied' | 'partial'
    | 'not_synced' | 'not_committed';
  appliedCount: number;
  skipped: Array<{ index: number; errorCode: string; errorMessage: string }>;
};
```

- index 为零基数组下标；appliedCount 是最终成功提交中的有效项数量，重复有效路径也逐项计数，不等于变化字段数量。
- 有跳过项为 partial；无跳过项且最终有实际变化为 applied、无差异为 unchanged；无可写状态始终为 not_required。
- 协议/提交失败为 not_synced，已丢弃候选不计入 appliedCount；主动停止未提交为 not_committed。
- 无可写状态且发生其他叙事错误时保持 not_required，不能提示“缺少状态尾块”。
- 沿用 run.failed 提示整轮状态未同步；Run completed 的 partial 结果由平台显示非阻断提示。
- 仅在权威状态事务提交后、确有状态差异时发布 state.changed；随后发布对应 Run 终态。该通知不额外承诺持久重放。
- 新叙事没有真实工具调用，不产生虚假的 toolCallId、toolResult 或 tool.failed。

## 9. 一次性会话数据清理

### 9.1 执行边界

**清理所有已有 session 是不可逆的业务数据删除。本次文档修订不执行清理。**只有后续明确执行包含该清理的实施/升级任务时，才运行以下迁移。

清理必须是版本控制的一次性升级，不能在每次启动、每轮叙事、切换预设或打开会话时重复执行。

### 9.2 当前仓库的真实关联范围

当前代码没有独立 runs、摘要、状态或会话事件表；这些信息分别存在 entries 与 sessions 中。

| 范围 | 删除内容 |
|---|---|
| entries | 所有会话条目，包括玩家消息、AI 原始响应与可见正文、toolResult、流式未完成条目、compaction、branch_summary |
| entries 内关联字段 | 消息状态快照、Run 终态、请求幂等记录、原始生成信息、metrics_json 及其他 ext_data |
| sessions | 全部会话记录，包括世界/预设/模型绑定、玩家角色、标题、tip、session 状态、usage_json、pendingRun |
| 服务端内存 | 已停止服务的 active Run、会话任务与缓存、订阅及世界运行占用；新进程从空会话集合开始 |
| 浏览器旧会话状态 | 旧会话页面的历史/草稿/iframe/SSE 状态及对应会话字号偏好 |

**entries.session_id 没有外键级联。必须先显式清理 entries，再清理 sessions，并包含孤立的旧 entries。**不能只删 sessions，也不删除承载这些数据的表或数据库文件。

浏览器已确认的会话持久化键为 `sr:session:<id>:reading-font-size`。客户端升级或旧会话 404 后，按旧会话/明确不存在的会话 id 定向清理；首次升级晚于新会话创建时不得删掉新会话设置。不得清空整个 localStorage。

当前不存在会话专属文件目录；不要凭想象删除工作区、媒体目录或世界源文件。

### 9.3 必须保留的非会话数据

- worlds 全部记录：世界卡、角色、开局、世界书、状态定义、UI、渲染规则、默认预设/模型绑定及 **global 当前状态**。
- presets 记录及用户正文；仅执行第 8 节明确的节点结构规范化。
- api_model_configs、凭据引用及系统凭据。
- app_settings，包括应用默认预设与默认模型。
- tags 与 tag_assignments；当前标签仅属于 world/preset。
- 世界卡原文件、source_file_path、source_sha256 与其他资源。
- 浏览器主题、密度、导航偏好等非会话设置。

不得调用删除 world 的路径来间接清空 sessions；该路径会继续删除世界、标签关系和源文件。不得删除整个 DB、dataDir 或重建全部预设。

### 9.4 实际执行时机与事务

现有启动顺序是获取数据目录独占锁 → openDatabase → recoverInterrupted → 创建运行时/应用 → 开放 HTTP。未来迁移应在持有独占锁、运行时尚未创建、HTTP 尚未开放时完成。

实施步骤：

1. 停止旧进程并等待其退出；不在仍有旧 Run 写入的数据库上升级。
2. 只读预检 schema 版本、受影响数量、非会话表及世界源文件记录；不打印正文或凭据。
3. 生成可恢复的一致性数据库备份，正确处理 WAL，不能仅复制主文件冒充完整备份。
4. 为本次升级增加新的版本门槛；以目前版本 1 为基线分配版本 2，若实施前版本推进则使用下一未占用版本。
5. 在同一升级事务内：定向规范化预设节点和世界书位置字段 → 删除 entries → 删除 sessions → 验证保护范围与规范化结果 → 写入新版本标记 → 提交。
6. 失败整体回滚、不推进版本、不启动对外服务；后续经问题修正再执行，不能在请求处理中静默重试删除。
7. 成功后再初始化 Runtime 并开放服务；再次启动检查版本后跳过该迁移。新数据库直接使用新规范，不执行旧会话删除逻辑。
8. 前端遇到旧会话不存在时释放页面资源、定向清理旧偏好并返回会话列表，不反复重连已删除会话。

当前 `user_version < 1` 的历史升级会重建预设，不得复用该策略或把版本降回 0。对已有但版本早于当前受支持基线的数据库，应在写入前拒绝自动升级并另行确定保留数据的迁移路径，不能先运行会清空预设的旧分支。空的新数据库与不受支持的旧数据库必须区分。

迁移验证保护范围以主键集合、计数及规范化允许范围为准；允许 presets.config_json、worlds.lorebook_json 的明确变动，其他非会话业务数据不得变化。
