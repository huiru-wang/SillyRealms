# 内置预设与世界卡初始化方案

## 目标与现状

服务端从仓库根目录 `initial-data/` 读取随版本发布的资源。第一批包含「标准叙事」和「小饭馆」。部署目录提供模板，SQLite 和配置的数据根目录保存用户实际使用的副本。新增内置内容只需提交资源文件和清单条目。

目前 `server.ts` 在监听前同步执行 `initialize()`。它在一个 SQLite 事务中补齐固定 ID 的预设和应用设置。预设模板来自 `modules/presets/default.ts`，其中两个节点使用 `postprocess.ts` 的提示词。普通世界导入用例负责暂存、校验 ZIP、发布文件、写世界与标签、失败补偿，`WorldService.prepareImport()` 每次生成 UUID。

现有 `resources/worlds/小饭馆.zip` 约 8.8 MiB，根部有 `world.json`，另含 3 个组件和 4 张图片。仓库忽略整个 `resources/`，Linux 部署从 Git 克隆运行，因此实施时应将原包逐字节复制到 `initial-data/worlds/` 并纳入 Git。原素材目录继续用于本地创作。

## 资源清单

建议 `initial-data/manifest.json` 使用以下内容。文件名可以保留中文。ID 负责数据库身份，文件名供加载器寻址，卡内名称用于展示。

```json
{
  "defaultPresetId": "sr-default-preset",
  "presets": [
    { "id": "sr-default-preset", "file": "标准叙事.json" }
  ],
  "worlds": [
    { "id": "sr-world-xiaofanguan", "file": "小饭馆.zip" }
  ]
}
```

- 路径相对于服务端模块位置解析，预设和世界分别定位在清单同级的 `presets/`、`worlds/`。支持测试注入临时资源根。切换工作目录或设置 `SERVER_DATA_ROOT` 只应影响各自对应的路径用途。
- 清单读取时校验结构、稳定 ID、分类内唯一性、默认预设引用、文件名和后缀。只允许对应子目录内的普通文件，拒绝目录穿越与符号链接逃逸。先检查清单所列文件存在及类型。预设在首次使用前按现有 codec 校验，世界 ZIP 只在需要安装时读取、解包。忽略未登记文件，便于明确控制发布内容。
- 以当前 `toPresetDocument(defaultPreset())` 的输出制作 JSON，采用现行导入导出协议，包括 `config_json.schemaVersion = 3`、`context_strategy`、`model_parameters`。迁移时比较两侧解析后的领域值，包括提示词、节点顺序及显式模型参数。已展开的两个后处理提示词写入 JSON，运行时针对缺失提示词的既有回退能力仍归 presets 模块。

## 启动流程

1. 加载清单和预设文档。由 PresetService 通过现有 codec 解析便携格式，装配时提供同一份默认模板给 `getDefault()` 和初始化流程。`GET /api/v1/presets/default` 继续返回原有领域形状和独立副本，不产生写入；用户编辑数据库预设不影响模板接口。
2. 在一个同步 SQLite 事务内依清单用固定 ID 补齐预设，沿用现有同名预设加后缀的逻辑，然后调用 `settings.ensure`。新库选择清单默认预设，默认模型为空。已有设置整条保留，包括用户自选项和显式空值。
3. 预设与设置提交后，按清单顺序检查每个世界的固定 ID。已存在则跳过文件导入。缺失时读取 ZIP，复用现有世界导入用例，继承当时的应用默认预设和模型，将原包和解包资源保存到数据根的 `worlds/<id>/`，并写入世界、标签及初始全局状态。
4. 给现有导入编排增加服务端内部的目标 ID 参数，传至 `prepareImport`。HTTP 上传保持原有签名、随机 UUID 和同名多次导入能力。启动入口 `await initialize()` 后再监听；文件读取、解压和发布均在 SQLite 事务外执行。

## 升级、删除与失败

| 场景 | 建议行为 |
| --- | --- |
| 空库首次启动 | 创建「标准叙事」、应用设置和「小饭馆」。模型和会话继续由用户创建。 |
| 老库升级 | 直接识别原有 `sr-default-preset`，缺什么补什么。已有同名手动导入世界使用独立 ID，其会话和状态继续归原世界。列表可能出现两个「小饭馆」。 |
| 重启或同一资源发布新版 | 已有 ID 保留用户副本，包括 revision、时间、管理字段、状态、资源和会话。新版模板用于新安装或补建，新增 ID 在下次启动安装。 |
| 用户删除内置条目 | 建议沿用当前默认预设的补齐语义。只要清单仍登记该 ID，下次启动就从发行模板重新创建。世界是全新副本，已删除的会话和游玩进度不会恢复。若产品需要记住永久删除，届时应显式保存逐项安装记录。 |
| 清单以后移除某项 | 已安装的数据和引用继续保留。清单只决定要补齐的条目。 |
| 资源或导入失败 | 报出资源类别、ID、相对文件名和具体原因，启动失败。预设与设置事务整体回滚其自身写入；逐世界复用现有补偿。前序已提交项保留，修正后重启从缺失项继续。 |
| 数据库无该世界，但目标目录已存在 | 这可能是文件发布后进程中断。按现有目标目录冲突处理，保留现场并给出数据根内的相对路径。管理员核对备份后移开残留目录，再重启补建。已有世界记录但资产丢失属于数据备份恢复问题，启动时不覆盖用户文件。 |

固定 ID 足以表达上述策略，无需新表或数据库版本迁移，也无需全局“已初始化”标记。示例包更新后，发布者应维持既有 ID；更换 ID 会被视为不同的内置条目。
