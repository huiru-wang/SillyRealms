> 整理日期：2026-11-10。
> 基线：当前 main（核对时 ae0e457），结合历史产品总纲、Session/WorldStory 设计及近期需求讨论。

## 1. 定位与当前边界

SR 是本地优先的世界卡客户端、创作台和多角色叙事运行环境；产品主路径是「世界卡库 → 世界详情 → 选择开局/角色 → 会话体验」。世界卡作者可以使用隔离的 React UI 及 SR SDK 定义会话呈现方式。

当前已具备的首版能力包括：世界卡 JSON 导入/导出及基本管理、角色/开局选择、预设与模型配置、会话创建与流式生成、工具修改状态、世界书/上下文装配、历史分页、WorldStory 默认 UI、创作者 UI/消息渲染、Token 统计和基础主题。以下待办不重复建设这些能力。

当前会话按连续历史运行。**分叉、重生和历史改写属于下一轮独立立项的功能**，本 Roadmap 仅保留其需求，不授权直接调整 Session/Entry 语义。

## 3. R1：世界线与消息操作（最高优先级）

**目标**：使用户真正拥有可探索的多条叙事走向，而非只能在单线聊天中不断续写。

### 3.1 面向玩家的能力

1. 查看当前会话的世界线关系：根节点、分叉点、每条分叉的首节点与叶子节点；长线可折叠。
2. 从指定历史节点选择既有分支并切换当前世界线，回到该分支最后的叙事位置。
3. 在受限节点创建新分支，避免编辑历史后悄悄覆盖原世界线。
4. 对**当前最后一条 AI** 提供「重新生成」与「续写」；历史 AI 的处理必须通过分支规则，不偷偷修改已存在后代。
5. 支持编辑玩家历史输入，并从该位置创建新的叙事分支；**不自动重算旧后续**。
6. 每个可分叉点建议最多 3 条分支（历史产品约束），达到限制时明确提示。

### 3.2 设计前必须确认

- 世界线数据模型：分叉点、父链、Run 归属、分支数、叶子节点选择，必须能与现有连续 Session 平滑分层，而不是直接改变默认链路。
- **状态隔离**：Message 状态应随分支恢复；Session / Global 状态是共享还是按分支恢复，需要明确语义，否则容易出现剧情与状态不一致。
- 重生和续写的 Tool 副作用、失败/中止、已有摘要覆盖边界与 Token Usage 归属。
- 切换世界线时的历史分页、滚动定位、运行中的发送互斥；移动端的世界线选择 UI。
- 历史编辑、重生/续写是否共享 Run 及请求幂等、版本/重复操作处理。
- 不自动删除原分支，也不静默更改已生成的历史数据。

### 3.3 最小验收

- 一次会话可以产生并切换两条可区分分支，切换后历史、当前 tip、消息状态一致。
- 最后一条 AI 能重生/续写，失败后原数据依然可访问。
- 编辑历史玩家输入生成新分支，旧分支不变；3 分支限制生效。
- 分页、压缩、SSE/工具消息和停止不破坏父链/状态一致性。

## 4. R2：世界卡可视化编辑（第二优先级）

**目标**：将 SR 从「导入世界卡后运行」扩展为「在 SR 中创作和维护世界卡」。

### 4.1 功能范围

- 世界基础信息：名称、简介、封面、标签及世界说明。
- 角色编辑：角色信息、可扮演标记、头像/描述、角色添加与删除。
- 开局编辑：开局正文、可选玩家角色、初始化状态预览与编辑。
- 世界书编辑：条目正文、触发词、排除词、激活规则、顺序/锚点。
- 状态编辑：Global / Session / Message 的声明、初始值与自然语言规则；提供 JSON/结构化双视图。
- 继续支持 JSON 导入/导出，并在保存前做同一份 Schema 校验。

### 4.2 决策边界

- 当前已有会话会读取世界最新内容，编辑可能影响后续运行；需明确变更提示、会话不兼容诊断和是否引入草稿/发布版本。
- 导入源文件与结构化世界卡不能被混为一份；编辑和导出行为须明确是否会覆盖原始导入文件。
- 暂不预设复杂多用户协作、发布平台或在线 Marketplace。
- 初版优先把现有世界卡字段编辑完整，而不是新建独立的可视化脚本语言。

### 4.3 最小验收

- 用户无需手改 JSON 即可创建/修改一个可运行的世界，配置角色、开局、世界书与状态并成功启动会话。
- 导出后再次导入不丢失受支持字段；无效状态规则和引用错误有可定位反馈。

## 5. R3：叙事透明度与会话恢复（第三优先级）

### 5.1 上下文与 Prompt 诊断

- 预览单轮实际启用的预设节点顺序、System Main、世界书/角色激活结果、摘要及保留历史范围。
- 世界书匹配可解释：命中词、排除词、when 结果、未加载原因。
- 上下文用量需区分 **Provider 实测 Token** 与 **按文本字节估算的结构比例**，不能把近似值当精确 Token。
- 显示最近摘要覆盖边界、历史保留策略及固定 Prompt 对预算的影响。
- 预览尽量走与真实生成共享的只读构建路径，不触发模型调用、不改变状态、不泄漏凭据。

### 5.2 状态变化追踪

- 按 Run 查看成功/失败状态变更及来源；必要时比较前后状态。
- 世界线场景需与 R1 的状态恢复设计一致，不另造一套互相冲突的历史状态逻辑。

### 5.3 断线恢复

- 区分网络断开、服务端 Run 仍执行、服务端已终止、用户主动停止。
- 重新进入时从服务端权威历史恢复最新 Run；是否需要流式 offset/事件补偿另行设计，不承诺当前 SSE 有重放保证。

## 6. R4：体验增强与扩展生态（低优先级）

- **AI 帮答**：根据当前剧情生成玩家可编辑的输入建议，不自动替玩家做决定。
- **图像/语音**：作为可选能力，独立处理资源管理、成本、模型适配及安全边界。
- **主题系统**：从当前亮暗主题升级为 Token/CSS Schema 驱动的导入、预览、切换；明确平台 UI 与作者 iframe/Markdown 的样式边界。
- **创作者 UI 工具**：常用 React UI 模板、可配置状态栏与组件预览，后续再评估可视化布局编辑器。
- **世界卡导入兼容**：优先研究结构数据转换，酒馆脚本、正则和外部扩展不能自动视作可信可执行代码。
- **长期平台方向**：世界卡版本、Android/Desktop、自定义 Provider 均保留为机会项，不属于近期 R1—R3 交付范围。

## 8. 分阶段推进原则

1. **每期先产品评审，再实施方案**：明确用户旅程、交互边界、存储/运行语义、移动端与验收样例；用户批准后再建立对应独立 plan 文件。
2. **R1 先验证数据语义**：尤其分支数量、Run 复用、Session/Global 状态共享、副作用与摘要边界。没有这些结论不开始跨层实现。
3. **R2 先确定编辑/发布语义**：世界数据修改对正在使用该世界的会话有什么影响，是主要产品风险。
4. **R3 优先复用运行时事实**：诊断展示应来自真实构建和持久化结果，不构建只在 UI 中看似正确的假数据。
5. **R4 不倒灌首版核心架构**：不为未来 Android/云同步/脚本运行预建大量抽象。
6. 保持单用户、本地优先、Web+Server 和创作者 iframe 隔离边界；不暗中扩展为云平台。
7. 每完成一个迭代，同步回写 Roadmap 的「当前状态」「落地文档」「验收证据」，避免历史计划被删除后失去追踪。
