# 预设采样参数设计

## 目标与边界

预设保存用户对温度、Top P、频率惩罚、存在惩罚的选择。预设与模型配置独立，可以跨会话复用。服务端在每次调用前按真实路由和思考模式逐项决定哪些值能生效。一个可选项被忽略时，其余参数和本次请求继续执行。

当前 Web 在 `features/presets/PresetLibraryPage.tsx` 用可留空的数字框编辑温度。服务端预设有独立的 API 校验、便携文件和 SQLite JSON 映射。主叙事通过 context 的 assemble 阶段组装请求，滚动摘要通过 prepareContext 的 summarize 回调组装请求，最终都经过 PiClient。这里适合共用同一组采样偏好和同一套发送规则。

## 参数与存储

| 显示名 | HTTP / 领域字段 | 存储 JSON / 便携字段 | 预设可保存范围（含端点） | 滑动步长 | 首次点「自定义」的起点 |
|---|---|---|---|---|---|
| 温度 | `temperature` | `temperature` | 0 至 2 | 0.01 | 1 |
| Top P | `topP` | `top_p` | 0 至 1 | 0.01 | 1 |
| 频率惩罚 | `frequencyPenalty` | `frequency_penalty` | −2 至 2 | 0.01 | 0 |
| 存在惩罚 | `presencePenalty` | `presence_penalty` | −2 至 2 | 0.01 | 0 |

以上是产品编辑范围。模型可以只接受其中一段，也可以排除端点。滑动步长只作用于拖动与方向键，手输、导入及回读保留原有合法精度，例如温度 0.735。四项均为可选有限数值，写入时拒绝 null、字符串和超出预设范围的值，明确填写的 0 必须保留。恢复默认即从完整的 modelParameters 中移除该键。

HTTP 保持 `config.schemaVersion: 1`，便携文件保持 `config_json.schemaVersion: 3`，SQLite 保持现有 JSON 列及版本。新 Server 能读原有数据和文件。旧 Server 的严格导入校验可能拒绝含新增键的文件。内置模板已有显式温度 1，继续保留；三个新增项初始均缺省。旧预设中缺省的温度继续缺省。共用四个采样键的明确读写映射，防止保存、复制、导入、导出走出不同结果。

## Web 交互

沿用 React/Vite 管理页、CSS Modules、共享控件和现有浅深主题 token。在「模型参数」下按温度、Top P、频率惩罚、存在惩罚排列，下面继续显示思考设置。区域只加一句说明「预设可跨模型使用。调用时仅应用当前模型支持的值。」

| 参数类型 | 控件与交互 |
|---|---|
| 有上下限的连续数值 | 同一行使用有数值端点的原生滑块与可精确输入的数字框，两者编辑同一草稿值。默认状态显示「模型默认」和「自定义」操作。点击自定义后才显示滑块、起点值和「恢复默认」。 |
| 布尔 | 思考开关使用现有 Switch。 |
| 枚举 | 思考深度沿用 Select 和既有联动，允许使用默认档位。 |
| 大范围整数 | 上下文与输出 token 预算沿用有整数校验的数字输入，保留两者之间的现有校验。 |

温度说明「值越低，措辞越稳定」；Top P 说明「值越低，下一步可选的词越少」；频率惩罚说明「正值抑制反复用词，重复越多，抑制越强」；存在惩罚说明「正值降低已用词再次出现的机会」。两个惩罚项在刻度中央标出 0。

桌面左侧放标题和说明，右侧放控件；窄屏改为上下布局，数字框和恢复操作保持可见。滑块采用共享原语，页面仅负责排列。滑块和输入框各有可区分的可访问名称并关联同一说明；可用方向键微调、Home/End 到达端点，所有操作具有可见焦点。只在实际编辑后标记草稿变化，通过现有「保存预设」提交。

数字输入允许暂时空白或负号，字段旁显示未完成／越界提示，保存和复制均需校验当前输入，避免提交上一个有效值。通过「恢复默认」清除覆盖和错误。切换记录、撤销和恢复服务端版本时同步局部输入状态。打开页面或复显滑块不会把已有精度量化为 0.01。编辑页没有会话模型上下文，所有预设项可编辑；切换应用默认模型不会删除或禁用某个预设值。

## 服务端调用

1. 在接受该轮、首次异步等待前，从已有快照提取四项可选采样偏好。主请求和摘要均传递同一份偏好；各自的输出预算、思考档位和取消信号继续走现有链路。context 与 narrative 只依赖模型边界的类型。
2. 在 `infrastructure/pi` 解析实际 SDK 模型和有效思考模式，包括不支持所选深度时 SDK 的回退，以及未显式发送思考字段时服务商的默认模式。只有能确定模式时才采用依赖模式的规则。不要根据前端开关或模型名片段猜测。
3. 在适配层维护小型、可审查的能力表。规则按实际 provider、API 协议、模型 ID、端点身份和必要的思考条件匹配。每项声明是否可覆盖、数值范围及端点开闭；遇到同时设置有限制的参数还要声明组合规则。优先复用 SDK 明确的限制，厂商文档及可验证路由补充缺口。SDK 的 `samplingParams` 与 `samplingParamsByThinkingLevel` 是默认参数，不能当作能力清单。第三方路由独立核对。
4. 逐项比较。预设未设置就沿用 SDK／服务商默认行为；值在已确认范围内则传入。未知、不支持、固定值、当前模式无效或值超出该路由范围时，仅省略该项用户覆盖。不要自动把 0.8 调成 0.95。若某路由禁止同时覆盖温度和 Top P，建议保留原有温度优先、忽略 Top P；只有已确认互斥才执行这条规则。
5. pi-ai 1.5.0 提供具名 `temperature` 及 OpenAI 兼容适配器的 `samplingParams`。按已核实的具体协议映射，后者仅构造白名单键。验证 SDK 默认值、分思考档位默认值与请求覆盖的合并优先级，包括同名温度；在兼容适配器上需要用户值最终胜出时，通过覆盖优先级正确的通道传一次。原生协议逐项核对已实现的 SDK 通道。保持 `onPayload` 为只读诊断，不借它注入字段。业务层、Web 和便携预设都不接收任意供应商请求体。检查最终请求字段是否符合预期；SDK 自带的合法默认值与预设覆盖分开断言。
6. 有明确设置被忽略时，在现有开发诊断中按参数记录原因（例如「当前模式不可调」「超出模型范围」「能力未确认」）。保持单次请求，不因采样参数发起探测、降级重试或新增会话事件。

### 首批可验证路由

| 实际路由 | 温度 | Top P | 两项惩罚 |
|---|---|---|---|
| OpenRouter 的 `openai/gpt-4o-mini`，Pi 目录中的 `openai-completions` | 可覆盖 | 可覆盖 | 两项均可覆盖。核对到该模型公布的 Azure、OpenAI 两个端点均列出四项，以可路由端点能力交集为准。[端点能力](https://openrouter.ai/api/v1/models/openai/gpt-4o-mini/endpoints) |
| 官方 `deepseek-v4-pro` | 非思考时可覆盖 | 非思考时接受 (0, 1]，思考时固定 | 省略。[DeepSeek 请求参数](https://api-docs.deepseek.com/api/create-chat-completion/) |
| 官方 `deepseek-flash` | 非思考时可覆盖 | 思考时可覆盖 [0.95, 1]，非思考时固定 | 省略。[DeepSeek 思考模式](https://api-docs.deepseek.com/zh-cn/guides/thinking_mode/) |

当前 Pi 目录中 OpenAI 官方 GPT-4.1 走 Responses。上一表的 OpenRouter 规则不能套用到这条路由。实施时亦应盘点现有温度调用，对已核实支持的原生协议保留具名温度；未登记的路由会停止透传旧预设温度，这是采用「仅发送已确认支持项」带来的行为变化。规则和依赖版本一同维护，应用发起叙事时无需在线拉取能力表。

## 验收示例

同一个预设显式设置温度 0.7、Top P 0.9、频率惩罚 0.4、存在惩罚 0。走上述 GPT-4o mini 路由时，四个值完整传出，包含 0。切换至官方 DeepSeek V4 Pro 非思考模式，只发送温度 0.7 和 Top P 0.9；切至思考模式则省略四个覆盖。切至官方 DeepSeek Flash 思考模式时，0.9 低于可调范围，同样省略；仅把预设 Top P 改为 0.97 后，该模式发送 0.97。每次切换，预设和 revision 均保持原样，主叙事与摘要执行一致的判定。
