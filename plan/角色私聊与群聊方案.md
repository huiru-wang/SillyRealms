## 1. 目标与推荐结论

在同一场游玩中支持主剧情、与世界角色的私聊、固定成员小群聊。私聊和群聊使用对话逻辑，有独立的提示词编排、参数、上下文组织和生成流程。

每次聊天使用三类上下文：

1. 公共上下文：同一 session 的世界背景、玩家身份、适用状态和可共同使用的主剧情背景。
2. 当前聊天上下文：本次私聊或群聊的参与角色、聊天信息、摘要与历史消息。
3. 角色经历：按本次参与角色分别组织其在其他聊天中获得的线索、约定、关系经历等，保留来源与知情归属。

聊天记录归属于 chat；角色经历逻辑上属于 session 中的角色，并可由其经历过的有效消息派生。角色从私聊进入群聊后，仍应记得私聊获得的相关信息；其他群成员不会因为它被注入模型就自动知情。

推荐采用：

- 一个 session 表示同一场游玩。
- session 内增加 chat，统一表示 main、direct、group。
- run 与 entry 明确归属于 chat；角色作为成员和实际发言者。
- 增加独立 chat 预设类型，与 narrative、reply_assist 平级。
- 平台提供默认聊天预设，session 统一绑定，所有私聊与群聊默认复用。
- 公共材料通过共用的材料构建能力提供；聊天不继承叙事主提示、节点顺序或后处理开关。
- 保留 session 全局消息提交顺序、状态继承链与运行锁。
- 小群聊首版推荐一次模型调用，生成一条 assistant entry 内的多个角色发言片段；模型接收分角色标注的经历材料并遵守角色知情约束。
- 角色跨聊天经历召回属于首版基础能力，不整体推迟到长期记忆模块；输入层面的严格角色隔离是单独的执行模式取舍。

## 3. 领域边界：session、chat、run、发言者

### 3.1 各对象职责

| 对象 | 职责 |
| --- | --- |
| session | 同一场游玩、玩家身份、共享世界进展、运行锁、总用量 |
| chat | 一段持续交流，承载类型、成员、名称和历史范围 |
| run | 某个 chat 的一次生成与结算 |
| entry | 持久化的用户消息、助手回复或压缩摘要 |
| 发言片段 | 一条助手回复中某个角色说出的内容 |
| 角色经历投影 | 从角色实际参与过的有效交流中选择相关材料，跨 chat 延续该角色的认知，不另建一份世界真相 |

归属、发言身份、知情范围分别表达：

- chatId：消息属于哪个聊天。
- characterId：具体由哪个角色发言。
- 知情范围：哪些角色已听到或观察到某个信息；不直接由上述两个字段替代。
- sourceChatId/sourceEntryId：某段经历从哪里产生，不等于以后只能在该 chat 使用。

固定成员的 direct/group 可以依据消息实际受众推导谁接触过其中的可见发言；主剧情的全知旁白、角色心声、系统指令、模型推理与隐藏能力块不能依成员列表自动赋予所有角色。

### 3.2 Chat 结构草案

以下为领域结构示意，最终数据库字段与传输格式在实施时统一定义：

~~~ts
type SessionChat = {
  id: string;
  sessionId: string;
  kind: 'main' | 'direct' | 'group';
  title: string | null;
  characterIds: string[];
};
~~~

推荐默认：

- 每个 session 自动创建一个 main chat，承载既有主剧情。
- direct 包含一个 NPC，玩家身份继承 session.userCharacterId。
- group 包含多个 NPC；同样成员可建立不同用途的群，群身份不由成员集合推导。
- main 不以固定成员数组限制叙事角色，继续使用主剧情的角色选择方式。
- 同 session、同一 NPC 的普通私聊默认复用一个 chat。
- 首版群成员固定；需要更换成员时创建新群，暂不定义中途入群的历史可见性。

### 3.3 持久化与一致性

新增 session_chats，作为 sessions 模块拥有的资源；首版成员可以用 JSON 保存，无须先建立独立成员模块。

entries 增加 chat_id，并建立按 session、chat、seq 查询的索引。所有消息和 compaction entry 均记录归属。

约束：

1. chat 必须属于请求中的 session。
2. 成员引用当前世界的稳定角色 ID，不以角色名称作为身份。
3. 一个 run 的所有 entry 属于同一个 chat。
4. run 受理时固定 chatId 和成员快照，后续 UI 切换不改变执行目标。
5. session 全局 seq、parentId、tipEntryId 保持当前语义。
6. 每个可用 session 具有默认 main chat。历史数据处理遵循实施时仓库的数据库版本策略；未发布阶段若不支持旧库，则明确使用新数据根，不暗中清空旧数据。本方案不强制另建历史兼容迁移。
7. 不为本功能新增 runs 表。

## 4. 预设方案：独立类型与官方默认同时采用

### 4.1 方案比较

| 方案 | 优点 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| 平台写死聊天提示词 | 配置最少 | 创作者无法充分调整表达、群聊节奏和上下文策略 | 作为默认模板，不作为唯一实现 |
| 叙事预设的聊天子配置 | 表面上只选择一个预设 | 同一对象内维护两种流程；替换叙事预设可能连带改变聊天 | 不推荐 |
| 私聊、群聊各建一个预设类型 | 区分明显 | 当前差异主要是成员与回应规则，无需复制两套类型和编辑器 | 首版不采用 |
| 独立 chat 类型，提供默认 | 可独立演进、编辑、导入导出，同时开箱即用 | 需避免让每个聊天都成为配置步骤 | 推荐 |

独立类型解决业务职责与演进边界；内置默认解决使用成本。

### 4.2 类型与实例

~~~ts
type PresetType = 'narrative' | 'chat' | 'reply_assist';
~~~

一个 chat 预设可以被多个私聊、群聊、session 复用。预设不保存具体聊天成员、历史消息或世界状态。

direct/group 是运行输入，不是两套预设类型。以后可以建立“自然私聊”“活跃群聊”等不同实例，仍使用 chat 类型。

### 4.3 默认绑定

首版只做“应用默认 → 会话绑定”两层：

1. initial-data 提供“标准角色聊天”预设。
2. 应用设置增加 defaultChatPresetId。
3. 创建 session 时把实际默认预设 ID 写入 runtimeConfig.chatPresetId。
4. session 内所有 direct/group chat 默认共用此绑定。
5. 会话设置允许更换聊天预设。

~~~ts
session.runtimeConfig = {
  narrativePresetId: '...',
  chatPresetId: '...',
  replyAssistPresetId: '...'
};
~~~

以上仅示意相关字段，现有 runtimeConfig 的其他字段继续保留。

改变应用默认只影响新建 session，不自动替换已有 session 的预设绑定；修改同一个预设实例的内容会影响后续生成。每次 run 在开始时捕获本次实际使用的配置。

首版不增加角色级、世界级、单 chat 级的多层运行时继承。单 chat 的可选 presetId 覆盖列为后续能力。

### 4.4 模型与参数

- 聊天默认沿用 session 已选择的模型。
- 采样参数、思考设置、输出长度与上下文策略来自 chat 预设。
- 后续如需“叙事用强模型、聊天用快速模型”，在会话聊天配置中增加模型覆盖。
- 不因新增 chat 类型而要求用户重新配置一个模型，也不为每个角色复制模型配置。

## 5. 聊天预设的节点与执行契约

### 5.1 推荐节点

| 节点 | 职责 | 材料来源 |
| --- | --- | --- |
| 聊天主提示 | 定义交流目标、角色表达、回复长度和对话规则 | chat 预设 |
| 玩家信息 | 玩家身份与必要设定 | session、世界卡 |
| 世界信息 | 适用背景与世界书 | 公共材料 |
| 当前状态 | 本次交流需要的共享状态 | 公共材料 |
| 公共剧情 | 主剧情有效摘要与近期进展，以背景形式注入 | main chat |
| 参与角色 | 当前私聊对象或群成员的设定 | 当前 chat |
| 角色经历 | 分角色注入跨聊天获得的相关信息、约定及来源 | 各角色实际参与过的有效交流 |
| 聊天历史 | 当前 chat 的摘要与历史消息 | 当前 chat |
| 当前输入 | 本轮用户消息，插入一次 | 当前 run |

chat 有自己的节点集合、模板变量和校验规则，不套用 narrative 的必需节点与顺序约束。基础编辑器、模板语法和部分材料节点实现可复用。

人物设定仍来自世界卡；聊天预设负责交流方式。公共剧情与角色经历的文本包装、预算可以在聊天预设中调整。

角色经历节点默认启用，由运行时按照角色实际经历提供材料。不得仅因换了 chat 就清空角色经历，也不得将分角色经历合并为所有成员共享的一段记忆。该基础历史投影不依赖长期记忆抽取模块已经上线。

### 5.2 预设与运行时的分工

| 预设负责 | 运行时负责 |
| --- | --- |
| 表达风格、回复组织、接话规则 | chatId、聊天类型、参与成员 |
| 节点编排与提示词包装 | 读取哪个 main/chat 的材料 |
| 上下文预算与聊天摘要策略 | 校验材料来源和实际可见范围 |
| 可选能力开关 | 校验发言者属于允许成员 |
| 正文生成要求 | 固定的可解析发言协议与输出校验 |

结构化发言协议由平台维护和注入。预设可以改变正文风格，不能随意修改平台用于识别角色与消息的协议字段。

### 5.3 后处理能力

聊天默认专注角色交流，不自动继承叙事预设的状态更新、行动建议或立绘开关。

需要状态更新等能力时，由聊天预设明确启用，并使用适合聊天场景的指令和写入范围。主舞台立绘首版不随普通聊天回复自动切换，聊天以头像和发言气泡展示。

## 6. 上下文组合：公共背景、当前对话与角色经历

### 6.1 公共上下文

每个私聊、群聊都可以使用当前 session 的适用背景：

- 世界背景及相关世界书。
- 玩家身份。
- 本次聊天适用的共享状态。
- 主剧情已有的有效摘要和近期进展中可作为背景的部分。

不把叙事预设的主提示、输出协议、能力指令、推理内容直接带入聊天。

“主剧情背景”“模型掌握的世界状态”“所有角色共同知道的事实”需要区分。不能只因为某信息存在于 main、角色 content 或共享状态中，就宣布所有角色都已经知道。无法确定角色受众的主剧情细节应保留来源与认知性质，或不作为共同已知材料注入。

### 6.2 当前聊天上下文

- direct/group 模式。
- 当前参与角色及其设定。
- 聊天名称、必要的主题信息。
- 当前 chat 的有效摘要与近期消息。
- 本轮用户输入。

当前聊天历史保持完整的交流归属。其他聊天的内容不直接拼进这一段对话序列，而是按对应角色的经历有选择地注入。

### 6.3 参与角色各自的经历

每个参与角色分别构建自己的经历块：

1. 在当前 session 的有效历史范围内，查找该角色实际参与过的其他 direct/group chat。
2. 读取这些聊天中有效、可见的交流正文及合法摘要；排除当前 chat，避免重复。
3. 按本轮话题、当前聊天近期交流和角色关系选择相关材料；重要线索、未决事项、约定与保密要求优先。
4. 保留来源 chat、消息/片段、时间、说话者，以及“谁告知谁”“是否证实”等信息。
5. 分角色注入，不能把所有成员的经历取并集后标成公共记忆。

角色的静态设定不等于已经发生的经历；仅在角色卡中提及另一个角色，也不代表其知道对方所有交流。

首版不要求每个角色新增独立记忆表。可从现有 chat 摘要和原文生成只读经历投影；后续通用记忆模块可作为另一种同样受来源与知情范围约束的材料来源。

### 6.4 三类材料的表达位置

公共剧情作为背景，角色经历按持有者分组，当前聊天作为实际对话序列。

示意：

~~~text
系统指令
  当前是玩家、A、B 的群聊。
  分角色使用其已知信息；私有经历不是本群已经公开的消息。

公共背景
  大家正在寻找失踪的钥匙。

A 的个人经历
  玩家曾在私聊中告诉 A：“钥匙可能在钟楼。”
  A 尚未验证；玩家要求先不要告诉 B。
  来源：与 A 的私聊及对应消息。

B 的个人经历
  B 知道钥匙失踪，正在等待新的调查方向。

当前群聊历史
  B：我们还没有找到新的方向。

本轮输入
  用户：大家有什么想法？
~~~

A 可以依据私聊经历决定回应或保留信息；B 不能把 A 的私人经历当成自己已经知道的内容。若 A 在本群实际说出钟楼线索，B 才从这条公开发言获得相应信息。

经历块只作为模型材料，不自动展示成群消息，也不直接写入本群摘要。

### 6.5 捕获与查询边界

在本次运行锁内捕获：

- session 真实 tip、配置、玩家身份。
- 当前 chat 与参与成员。
- 公共剧情材料的读取边界。
- 当前 chat 的历史与本轮输入。
- 每个参与角色的有效经历来源、摘要覆盖和版本边界。
- 当前状态与角色、世界书等材料。

ChatContext 的业务输入至少包含 sessionId、chatId，以及本次解析后的预设/模型选择；执行控制与业务选择分开。

chatId 来自已受理请求，不读取会随界面切换而变化的 session.activeChatId。跨聊天经历仍限定在同一 session，不跨故事线自动读取。

## 7. 预算与摘要

### 7.1 三类历史材料分别处理

| 内容 | 处理方式 |
| --- | --- |
| 公共剧情 | 读取已有合法主剧情摘要和近期片段，保留来源及必要的知情限定 |
| 当前聊天摘要 | 只压缩当前 chat 实际可见的消息，保存为该 chat 的 compaction |
| 当前聊天近期消息 | 优先保留完整轮次和实际发言者 |
| 分角色经历 | 从角色实际经历过的其他聊天选择相关摘要或原文，每个角色有明确归属和预算 |
| 本轮输入 | 完整保留且只插入一次 |

为公共背景和各角色经历预留预算，剩余空间用于当前聊天历史。不能等到当前聊天填满窗口后再把所有角色经历静默丢弃。

相关性与重要性优先于盲目加载所有历史。最近告知的重要线索、未决问题、明确约定与保密要求应优先保留；材料过多时按预设预算裁剪，不声称每一轮完整载入角色所有人生经历。

若主剧情尚无摘要，可以使用预算内近期完整轮次。发起聊天不顺便触发并持久化一轮主剧情摘要。

### 7.2 摘要保留认知性质

摘要必须保留：

- 谁说了什么、对谁说、发生在何处或哪个 chat。
- 信息是转述、猜测、计划、否定、谎言还是已证实结果。
- 重要线索、承诺、未决事项及明确的保密要求。
- 本轮实际公开了哪些内容；不能把仅供模型参考的个人经历写成群成员已知。

例如，原文“玩家私下告诉 A：钥匙可能在钟楼，先不要告诉 B”，不能压缩成无来源的“钥匙在钟楼”。

群聊摘要只根据群中实际可见发言生成。即使模型为生成群聊读过 A 的私有经历，未公开的部分也不能进入群聊摘要。

### 7.3 复用来源，不复制整份记忆

- 公共背景每轮重新读取，不反复复制到每个聊天摘要。
- 个人经历从原聊天的有效来源投影，不为每次群聊复制一套角色长期记忆。
- 同一来源可被多个确实经历过它的角色引用，注入时保留每个角色的归属。
- A 将部分信息在群中说出后，B 的后续经历可引用这条已保存的群聊发言；不需要把 A 的整段私聊复制给 B。
- 当有效摘要未覆盖本次需要的关键细节时，可以根据当前话题检索原文补充；不能把摘要未提及当作角色从未得知。
- 长期记忆模块接入后沿用来源有效性和按角色选择，避免再维护一套互相竞争的世界事实。

### 7.4 摘要归属与有效性

- 先确定有效历史，再根据当前聊天和角色经历来源选择材料。
- 摘要带聊天归属、覆盖边界及来源校验；角色/受众相关信息参与使用范围判断。
- 其他 chat 的摘要不能冒充本 chat 的历史摘要，但可以作为有资格读取该来源的角色经历材料。
- 来源编辑、删除或重生成后，失效摘要和经历投影不再使用，重新从有效来源构建。
- “被总结历史的末条”与“持久化的追加前驱”分开。
- 保存聊天摘要仍接整局真实 session tip，并归属当前已受理 run 和 chat。
- 公共主剧情与其他源 chat 摘要在当前聊天构建中只读。

## 8. 私聊与群聊的生成方式

### 8.1 首版统一调用流程

- 私聊由当前目标角色回应。
- 群聊由模型根据上下文安排一个或多个允许成员回应。
- 不要求每个群成员每轮都说话。
- 不替玩家决定发言或行动。
- 群聊首版不引入每角色独立 Agent、自主循环或并行模型调用。

### 8.2 单 assistant entry 内的多角色发言

保留一次 run 对应一条 assistant entry 的基本执行身份，内部以结构化片段表示角色发言。

以下仅表示领域语义，不是现有 API；实际存储字段和模型输出协议需在实施时一起定稿：

~~~json
{
  "role": "assistant",
  "chatId": "chat-investigation",
  "segments": [
    {"characterId": "alice", "content": "我去看看西侧房间。"},
    {"characterId": "bob", "content": "那我留在这里等你们。"}
  ]
}
~~~

约束：

- LLM role 保持 user/assistant，角色身份使用稳定 characterId。
- 不通过“姓名：”等正文模式猜测身份。
- 发言者必须属于本次允许成员。
- 流式投影能识别当前发言片段，UI 按片段显示气泡。
- 持久化回放、模型历史和摘要均保留发言身份及顺序。
- 整条 assistant entry 是首版编辑、重生成和状态结算单位。
- 若启用状态更新，在整轮回复后统一处理，不让每个气泡独立结算。
- 基础角色经历连续性在首版支持。若要求各角色输入严格隔离，则采用逐角色构建和顺序调用，不能把同一次模型请求中的文字分区称为输入隔离。
- 一轮群聊中的发言按实际片段顺序传播信息。后续角色可使用之前已公开片段中的内容，不能在相关片段出现之前提前获知；持久化后的可见发言成为以后经历的来源。

## 9. 世界状态、顺序与重生成

### 9.1 推荐的剧情语义

私聊、群聊默认是当前世界内真实发生的交流，与主剧情属于同一条世界线。

切换聊天只改变交流上下文，不切换世界状态。若聊天明确更新了关系或约定，回主剧情后仍保留这些变化。

### 9.2 历史尾部与状态 tip 分开

当前聊天继续使用整局最新有效状态，不能从该 chat 的最后一条消息恢复旧状态。

~~~ts
chatHistory;       // 当前聊天的上下文历史
sessionTipEntryId; // 整局状态读取和追加位置
~~~

既有 global/session/message 状态作用域沿用当前定义。chat 不新增一份独立世界状态。

### 9.3 聊天的状态更新

推荐默认：

- 聊天轮次不自动推进世界时间、移动人物或切换主场景。
- 只有显式启用聊天状态更新时，才执行相关后处理。
- 创作者配置适用状态根，服务端通过 allowedRoots 等现有基础校验写入范围。
- 时间、位置等语义不能靠程序猜字段名称。
- allowedRoots 控制写入，不能替代读取可见性。
- 听到线索不自动将线索内容写成世界真相。经历先保留“某角色听某人声称某事”，当前事实更新仍依真实发生与可确认变化。

### 9.4 锁与历史操作

- 继续使用 session 级串行运行锁。
- 用户可切聊天浏览、编辑草稿；同一 session 不同时执行多个写状态的生成。
- 只允许重生成整局最新 run，不能把“当前 chat 最新”当作“整局最新”。
- 不新增按 chat 独立回滚或自动重算后续跨聊天状态的能力。
- 后续开放更早消息的重演时，需单独设计对后续主剧情与其他聊天的影响。

## 10. 角色知情与跨聊天记忆：首版必须延续

### 10.1 对原方案的修正

原方案仅加载“公共上下文＋当前 chat”，并把跨聊天角色记忆全部列为后续，会造成角色更换聊天后失去此前私聊获得的信息。

修正为：角色跨聊天经历召回是首版基本能力；完整长期记忆管理和严格输入隔离可按不同范围另行演进。

Chat 决定消息在哪里发生；角色决定谁经历过、谁知道。信息的来源是某个私聊，不表示它以后只能在该私聊中使用。

### 10.2 关键线索示例

| 时点 | A 的经历 | B 的经历 |
| --- | --- | --- |
| 玩家私下告知 A“钥匙可能在钟楼”并要求保密 | 知道玩家提供了钟楼线索、信息尚未验证、存在保密要求 | 未获知钟楼线索 |
| A、B 进入同一群聊，尚未公开线索 | A 仍保留上述经历，可以选择如何回应 | B 不因进入同群或模型读过 A 的经历而自动知情 |
| A 在群中说“可以去钟楼找找” | A 保留原有经历，并知道自己在群里说过这句话 | B 获得 A 公开说出的线索，可按当时语境作合理推断 |
| B 之后进入另一段交流 | A 的原始私聊来源仍保留在 A 的经历中 | B 可回忆群中听到的线索，来源是群聊发言 |

“钥匙的位置线索”“玩家与 A 私聊过”“线索最初由谁提供”“双方有保密约定”是不同的信息。只公开其中一项，不代表其余内容一起公开。

A 是否转述由人物行为和当前对话决定，不由系统自动同步；未实际说出的内容不传播给其他角色。

### 10.3 首版最小实现：角色经历投影

无需先建立完整的独立记忆库：

1. 固定成员 direct/group 的可见发言，以实际参与者为可经历者。
2. 对每个待生成角色，选择其参与过的其他 chat 中有效摘要与相关原文。
3. 保留 sourceChatId、来源消息/片段和角色归属，按角色注入。
4. 当前聊天的可见历史为该聊天成员提供共同的交流依据。
5. 角色公开转述被保存后，接收者以后可以直接从这条新消息重建经历。
6. 原始私聊未公开的内容继续只作为原参与角色的经历来源。

这是一种基于既有记录的上下文投影，不是给每条消息复制全量角色记忆，也不增加自动知识传播的写账系统。

固定成员只简化可见交流的受众判断；系统指令、推理、隐藏能力输出、全知旁白、作者设定和心声不能一并视作所有成员听到的话。

### 10.4 单模型与严格隔离的取舍

首版保留单模型多角色生成时：

- 模型会读取多个角色各自的经历块。
- 用明确归属、来源和生成规则约束谁知道什么。
- 角色记忆连续性作为必要能力，避免无来源知情作为生成行为的验收目标。
- 角色之间没有输入层面的硬隔离；文字分区本身不能证明秘密绝不会被错误使用。

若产品要求严格控制各角色可见输入，需改为按角色顺序调用：

- A 的请求只包含 A 可见背景、当前交流和 A 自己的经历。
- 保存或接续 A 实际公开的发言。
- B 的请求只包含 B 自己可见的材料，以及 A 此前实际公开的部分；不能用“你不知道某个秘密”的句子反而把秘密正文注入 B。
- 一轮内仍可复用 run 的外层调度、用量与结算概念，但这属于执行策略变更。

两种模式的区别是输入边界与调用成本，不能把单模型方式包装成严格角色隔离。

### 10.5 主剧情与 AI 帮答的适用方式

同一角色返回主剧情时也应保留相关聊天经历。主剧情可以作为全知叙事者读取分角色材料，但生成时仍区分叙事者知情和人物知情。

不能把世界卡列出的所有角色都视为每个主剧情事件的目击者。具有明确受众或观察关系的主剧情内容可成为对应角色经历；不明确的旁白保留认知边界。

AI 帮答代表玩家生成草稿，应依据玩家实际可知的经历构建，不自动获得其他角色独有、玩家从未得知的私人材料。

### 10.6 与记忆模块的衔接

[记忆模块方案](记忆模块方案.md)中的 session 归属、来源消息、版本与有效性仍然适用。角色知情是另一个选择维度，不用把 chat 改造成与 session 并列的故事线。

后续长期记忆需要支持按知情角色或角色经历选择材料；只在正文里提到某个角色，不等于该角色知道这条记忆。世界关联、来源聊天、内容涉及的人物、实际知情者应分别表达。

本次只修订聊天方案中的接入要求，不把尚未实现的通用记忆模块视为前置条件，也不建设完整的事实与知识关系图。

## 11. Host、SSE 与 SDK

### 11.1 状态归属

| 内容 | 归属 |
| --- | --- |
| 玩家、当前世界状态、总用量、运行锁 | session |
| 历史页、分页游标、滚动位置、草稿 | chat |
| 角色经历投影 | session 中的角色；来源可跨多个 chat，服务于模型上下文 |
| 生成目标与流式回复 | 受理时固定的 chat |
| 行动建议 | 绑定发起 chat，按整局新轮次失效 |
| 事件连接 | session 一条 SSE，由 Host 分发 |
| 角色气泡/头像 | 当前 chat |
| 主舞台立绘 | 独立展示能力，普通聊天默认不自动改变 |

### 11.2 运行与恢复

- 一个 SessionWorkspace 持有共享运行事实和单条 SSE。
- 运行、消息、建议等相关事件携带 chatId。
- 共享 state.changed 继续按 scope 同步，不因为切换 chat 创建不同真相。
- 服务端按 chat 查询历史和分页；不能只在 WorldStory 过滤气泡。
- 切换 chat 后，旧请求的分页或帮答结果不覆盖新聊天。
- 当前活跃 run 显示其实际所属 chat，切换界面不取消或转移运行。
- 刷新后恢复当前聊天历史，同时读取整局活动运行状态。

### 11.3 AI 帮答

帮答继续作为独立用途和预设类型。其材料选择需要识别当前 chat，使用适用公共背景、当前聊天来源和玩家可知经历；不把群聊生成时所有 NPC 的私有材料合并给玩家。

帮答草稿绑定原 chat 和请求身份，晚到结果不能写进另一个聊天的输入框。

### 11.4 行动建议

沿用“新一轮同步受理成功即失效”的产品规则：

- 任意 chat 新 run 受理后，整局旧建议失效。
- 新建议只归属本次发起 chat。
- 刷新或切回旧 chat 时，不恢复早于整局最新轮次的过时建议。
- 复用现有历史同步与恢复能力，不新增独立恢复框架。

### 11.5 SDK 方向

与待实施的作者 SDK 治理方案保持一致：

- Host 负责真实运行状态、查询范围、去重和恢复。
- frame/作者组件消费当前聊天的投影和命令能力。
- 不为 main/direct/group 复制三套 Session、History、Snapshot hooks。
- 不由作者组件自行拼接跨聊天模型上下文；角色经历由服务端按角色资格选择，不能把模型输入中的个人经历块直接广播成群消息。
- 聊天选择与创建能力作为小范围入口补充，具体公开 API 在统一 SDK 契约中定稿。

## 12. 服务端组织与复用

新增 prepareChatContext 和聊天执行入口。它们复用基础能力，但不调用“先完整构建叙事，再替换主提示”的流程。

复用：

- 模块公开的世界、角色、状态、历史读取。
- 模板语法和变量展开。
- token 估算与模型预算。
- 历史投影、摘要模型调用等基础工具。
- 模型适配、会话锁、消息持久化、SSE 基础设施。

独立：

- chat 类型节点校验、编排与变量范围。
- 公共背景、当前聊天与分角色经历的组合。
- 参与成员和发言身份约束。
- 聊天输出协议、流式投影和选用后处理。

保持项目既有分层：

- 路由处理传输；业务规则在 Service。
- chat 表和 entries 由 sessions 模块管理。
- 跨模块写流程与提交后事件由 usecases 编排。
- context 负责构建请求，不反向依赖 SSE 或其他执行用例。
- StateService 保持计算职责；持久化由表属主 Service 完成。
- 不为本次需求引入通用 runtime、执行图或 Agent 框架。

## 13. 首版范围与后续能力

### 13.1 推荐首版

1. session 内 main/direct/group chat。
2. 聊天归属贯穿 entries、运行、查询、摘要和事件。
3. 独立 chat 预设类型、官方默认、应用默认及 session 绑定。
4. 公共主剧情背景、当前聊天上下文与分角色跨聊天经历共同参与生成。
5. 私聊、群聊共用类型与一套对话执行流程。
6. 群聊单次调用、单 assistant entry 内多角色发言。
7. 全局状态链、session 锁和整局最新 run 重生成规则。
8. 聊天历史、草稿、帮答、建议和刷新恢复。
9. 固定群成员、普通聊天头像气泡展示。
10. 基础角色记忆连续性：私聊得知的重要线索可在后续群聊或主剧情按该角色视角使用，实际公开发言再成为接收者的经历来源。

### 13.2 后续能力

- 单个 chat 覆盖预设与模型。
- 群成员动态加入、退出及入群前历史策略。
- 输入层面的严格角色隔离、规模化角色长期记忆管理；基础跨聊天经历召回已属于首版。
- 每角色独立调用、主动发言与自主调度。
- 跨聊天更早轮次的重生成和状态重演。
- 跨群自动转述、完整事实/知识系统。

## 15. 实施顺序与验收重点

### 15.1 建议顺序

1. 定稿 Chat、归属、chat 预设与输出语义契约。
2. 实现表结构、默认 main、默认聊天预设与绑定，遵循实施时的数据版本策略。
3. 构建公共背景、当前聊天和分角色经历三类 context，明确资格选择、摘要、认知性质与预算边界。
4. 实现聊天执行、结构化发言、持久化和事件。
5. 接入 Host、UI、SDK、草稿、帮答与恢复。
6. 用函数级测试及项目既有检查验证关键行为，更新对应正式契约文档。

### 15.2 核心验收

- 当前格式会话内主剧情与聊天状态保持连续；旧库处理符合仓库版本策略，不暗中清空用户数据。
- 所有新 run、entry、摘要和事件有一致聊天归属。
- 每个私聊、群聊同时拥有适用公共背景、自身历史和参与角色的相关经历。
- 玩家私下告诉 A 关键线索后，A 参与群聊时的个人经历投影包含该线索、来源及保密约定；B 的个人经历和公共材料不因此加入该内容。
- B 单独聊天时不能直接读取未参与的 A 私聊；A 所在群可以为 A 读取相关私聊经历，并保持个人归属。
- A 在群里实际说出线索后，B 的后续经历能从已保存群消息召回公开部分，不自动带入未公开的私聊来源和保密约定。
- 同一轮群聊的后续发言可使用此前已公开片段；生成行为用例检查其他角色不会提前表现出无来源知情。
- 群摘要只覆盖可见群消息，不能把模型读过但未公开的个人经历记为群共同记忆。
- 摘要保留转述、猜测、未验证、否定和保密等性质，不把听闻改写成世界真相。
- 对话源消息编辑、删除或重生成后，相关失效摘要与经历投影不再使用；尚存的公开转述仍按其自身来源处理。
- 结构级的来源/角色归属测试与模型生成行为评测分别报告，不把单请求分区视为严格输入隔离证明。
- 公共剧情作为背景注入，当前对话角色与用户输入位置正确，输入不重复。
- 聊天摘要不复制整份公共背景、不覆盖其他聊天摘要，并接整局真实 tip。
- 从旧聊天继续时使用整局当前状态。
- 独立 chat 预设可正常编辑、导入导出；默认配置开箱可用。
- 更换应用默认不替换已有 session 的绑定；更换会话聊天预设作用于后续聊天生成。
- 群聊只允许当前成员发言，发言身份在流式、持久化、历史和摘要中一致。
- 切换聊天不转移正在运行的回复，不串分页、草稿或帮答结果。
- 建议在整局新 run 受理时失效，新结果仅归属发起 chat。
- 某聊天的局部最新回复不是整局最新时，重生成按现有规则拒绝。
- 对话能力不意外继承叙事主提示、立绘或其他未启用后处理。

## 16. 实施前仍需定稿的细节

以下局部细节不影响本方案主要架构，在正式实施时确定：

- chat 输出的精确线协议、segments 的最终存储字段与流式事件形式。
- 当前聊天、公共背景、分角色经历的默认预算、摘要提示词、重要线索保留与原文检索参数。
- 聊天首版需要默认开启哪些可选能力，以及允许更新的状态根配置入口。
- chat 管理、发送和查询的最终路由与 SDK 命名，需与待实施的 SDK 治理方案协调。

这些细节应在实现前形成可验证契约；不通过复用完整叙事流程隐式决定。
