## 1. 目标与推荐结论

在同一场游玩中支持主剧情、与世界角色的私聊、固定成员小群聊。私聊和群聊使用对话逻辑，有独立的提示词编排、参数、上下文组织和生成流程。

每次聊天都使用两类上下文：

1. 公共上下文：同一 session 的世界背景、玩家身份、适用状态和公共主剧情进展。
2. 当前聊天上下文：本次私聊或群聊的参与角色、聊天信息、摘要与历史消息。

推荐采用：

- 一个 session 表示同一场游玩。
- session 内增加 chat，统一表示 main、direct、group。
- run 与 entry 明确归属于 chat；角色作为成员和实际发言者。
- 增加独立 chat 预设类型，与 narrative、reply_assist 平级。
- 平台提供默认聊天预设，session 统一绑定，所有私聊与群聊默认复用。
- 公共材料通过共用的材料构建能力提供；聊天不继承叙事主提示、节点顺序或后处理开关。
- 保留 session 全局消息提交顺序、状态继承链与运行锁。
- 小群聊首版采用一次模型调用，生成一条 assistant entry 内的多个角色发言片段。

## 3. 领域边界：session、chat、run、发言者

### 3.1 各对象职责

| 对象 | 职责 |
| --- | --- |
| session | 同一场游玩、玩家身份、共享世界进展、运行锁、总用量 |
| chat | 一段持续交流，承载类型、成员、名称和历史范围 |
| run | 某个 chat 的一次生成与结算 |
| entry | 持久化的用户消息、助手回复或压缩摘要 |
| 发言片段 | 一条助手回复中某个角色说出的内容 |

归属、发言身份、知情范围分别表达：

- chatId：消息属于哪个聊天。
- characterId：具体由哪个角色发言。
- 知情范围：哪些角色可以获知某个事实；不直接由上述两个字段替代。

### 3.2 Chat 结构草案

以下为领域结构示意，最终数据库字段与传输格式在实施时统一定义：

~~~ts
type SessionChat = {
  id: string;
  sessionId: string;
  kind: 'main' | 'direct' | 'group';
  title: string | null;
  characterIds: string[];
};
~~~

推荐默认：

- 每个 session 自动创建一个 main chat，承载既有主剧情。
- direct 包含一个 NPC，玩家身份继承 session.userCharacterId。
- group 包含多个 NPC；同样成员可建立不同用途的群，群身份不由成员集合推导。
- main 不以固定成员数组限制叙事角色，继续使用主剧情的角色选择方式。
- 同 session、同一 NPC 的普通私聊默认复用一个 chat。
- 首版群成员固定；需要更换成员时创建新群，暂不定义中途入群的历史可见性。

### 3.3 持久化与一致性

新增 session_chats，作为 sessions 模块拥有的资源；首版成员可以用 JSON 保存，无须先建立独立成员模块。

entries 增加 chat_id，并建立按 session、chat、seq 查询的索引。所有消息和 compaction entry 均记录归属。

约束：

1. chat 必须属于请求中的 session。
2. 成员引用当前世界的稳定角色 ID，不以角色名称作为身份。
3. 一个 run 的所有 entry 属于同一个 chat。
4. run 受理时固定 chatId 和成员快照，后续 UI 切换不改变执行目标。
5. session 全局 seq、parentId、tipEntryId 保持当前语义。
6. 既有 session 创建 main chat，已有 entry 回填到 main；不以支持聊天为由清空已有数据。
7. 不为本功能新增 runs 表。

## 4. 预设方案：独立类型与官方默认同时采用

### 4.1 方案比较

| 方案 | 优点 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| 平台写死聊天提示词 | 配置最少 | 创作者无法充分调整表达、群聊节奏和上下文策略 | 作为默认模板，不作为唯一实现 |
| 叙事预设的聊天子配置 | 表面上只选择一个预设 | 同一对象内维护两种流程；替换叙事预设可能连带改变聊天 | 不推荐 |
| 私聊、群聊各建一个预设类型 | 区分明显 | 当前差异主要是成员与回应规则，无需复制两套类型和编辑器 | 首版不采用 |
| 独立 chat 类型，提供默认 | 可独立演进、编辑、导入导出，同时开箱即用 | 需避免让每个聊天都成为配置步骤 | 推荐 |

独立类型解决业务职责与演进边界；内置默认解决使用成本。

### 4.2 类型与实例

~~~ts
type PresetType = 'narrative' | 'chat' | 'reply_assist';
~~~

一个 chat 预设可以被多个私聊、群聊、session 复用。预设不保存具体聊天成员、历史消息或世界状态。

direct/group 是运行输入，不是两套预设类型。以后可以建立“自然私聊”“活跃群聊”等不同实例，仍使用 chat 类型。

### 4.3 默认绑定

首版只做“应用默认 → 会话绑定”两层：

1. initial-data 提供“标准角色聊天”预设。
2. 应用设置增加 defaultChatPresetId。
3. 创建 session 时把实际默认预设 ID 写入 runtimeConfig.chatPresetId。
4. session 内所有 direct/group chat 默认共用此绑定。
5. 会话设置允许更换聊天预设。

~~~ts
session.runtimeConfig = {
  narrativePresetId: '...',
  chatPresetId: '...',
  replyAssistPresetId: '...'
};
~~~

以上仅示意相关字段，现有 runtimeConfig 的其他字段继续保留。

改变应用默认只影响新建 session，不自动替换已有 session 的预设绑定；修改同一个预设实例的内容会影响后续生成。每次 run 在开始时捕获本次实际使用的配置。

首版不增加角色级、世界级、单 chat 级的多层运行时继承。单 chat 的可选 presetId 覆盖列为后续能力。

### 4.4 模型与参数

- 聊天默认沿用 session 已选择的模型。
- 采样参数、思考设置、输出长度与上下文策略来自 chat 预设。
- 后续如需“叙事用强模型、聊天用快速模型”，在会话聊天配置中增加模型覆盖。
- 不因新增 chat 类型而要求用户重新配置一个模型，也不为每个角色复制模型配置。

## 5. 聊天预设的节点与执行契约

### 5.1 推荐节点

| 节点 | 职责 | 材料来源 |
| --- | --- | --- |
| 聊天主提示 | 定义交流目标、角色表达、回复长度和对话规则 | chat 预设 |
| 玩家信息 | 玩家身份与必要设定 | session、世界卡 |
| 世界信息 | 适用背景与世界书 | 公共材料 |
| 当前状态 | 本次交流需要的共享状态 | 公共材料 |
| 公共剧情 | 主剧情有效摘要与近期进展，以背景形式注入 | main chat |
| 参与角色 | 当前私聊对象或群成员的设定 | 当前 chat |
| 聊天历史 | 当前 chat 的摘要与历史消息 | 当前 chat |
| 当前输入 | 本轮用户消息，插入一次 | 当前 run |

chat 有自己的节点集合、模板变量和校验规则，不套用 narrative 的必需节点与顺序约束。基础编辑器、模板语法和部分材料节点实现可复用。

人物设定仍来自世界卡；聊天预设负责交流方式。公共剧情的文本包装与预算可以在聊天预设中调整。

### 5.2 预设与运行时的分工

| 预设负责 | 运行时负责 |
| --- | --- |
| 表达风格、回复组织、接话规则 | chatId、聊天类型、参与成员 |
| 节点编排与提示词包装 | 读取哪个 main/chat 的材料 |
| 上下文预算与聊天摘要策略 | 校验材料来源和实际可见范围 |
| 可选能力开关 | 校验发言者属于允许成员 |
| 正文生成要求 | 固定的可解析发言协议与输出校验 |

结构化发言协议由平台维护和注入。预设可以改变正文风格，不能随意修改平台用于识别角色与消息的协议字段。

### 5.3 后处理能力

聊天默认专注角色交流，不自动继承叙事预设的状态更新、行动建议或立绘开关。

需要状态更新等能力时，由聊天预设明确启用，并使用适合聊天场景的指令和写入范围。主舞台立绘首版不随普通聊天回复自动切换，聊天以头像和发言气泡展示。

## 6. 上下文组合：公共背景与当前对话

### 6.1 公共上下文

每个私聊、群聊都可以使用当前 session 的公共材料：

- 世界背景及相关世界书。
- 玩家身份。
- 本次聊天适用的共享状态。
- 主剧情已有的有效摘要。
- 摘要未覆盖的近期主剧情进展。

不把叙事预设的主提示、输出协议、能力指令、推理内容直接带入聊天。

这里的“公共”首先表示本方案约定的共享材料来源。主剧情全文、完整角色提示或全部状态并不天然代表所有角色共同知晓的事实；严格知情过滤见第 10 节。

### 6.2 当前聊天上下文

- direct/group 模式。
- 当前参与角色及其设定。
- 聊天名称、必要的主题信息。
- 当前 chat 的有效摘要。
- 当前 chat 的近期消息。
- 本轮用户输入。

其他私聊和其他群聊原文、摘要默认不加入当前聊天。

### 6.3 两类历史使用不同的表达位置

公共剧情以明确标注来源的背景记录注入；当前聊天以真实连续对话注入。

示意：

~~~text
系统指令
  聊天规则、玩家与参与角色资料、世界背景、当前状态

公共剧情背景
  玩家与 A 今天上午在大厅发现了一封信。
  玩家刚询问过东侧房间的情况。

当前私聊摘要
  玩家此前约好晚上单独与 A 交流。
  A 尚未回答信件来源的问题。

当前私聊历史
  用户：你现在方便说话吗？
  A：方便，怎么了？

本轮输入
  用户：刚才那封信，你是不是见过？
~~~

不把主剧情原始 user/assistant 消息与私聊记录无标识地拼成一个对话序列。公共剧情中的多角色旁白应作为背景，不改变当前聊天的生成任务。

### 6.4 捕获与查询边界

在本次运行锁内捕获：

- session 真实 tip、配置、玩家身份。
- 当前 chat 与参与成员。
- 公共剧情材料的读取边界。
- 当前 chat 的历史与本轮输入。
- 当前状态与角色、世界书等材料。

ChatContext 的业务输入至少包含 sessionId、chatId，以及本次解析后的预设/模型选择；执行控制与业务选择分开。

chatId 来自已受理请求，不读取会随界面切换而变化的 session.activeChatId。

## 7. 预算与摘要

### 7.1 两种历史分别处理

| 内容 | 处理方式 |
| --- | --- |
| 公共剧情 | 读取主剧情已有合法摘要和未覆盖的近期完整轮次；按公共背景预算选择 |
| 当前聊天摘要 | 只压缩当前 chat 的消息，保存为该 chat 的 compaction |
| 当前聊天近期消息 | 优先保留完整轮次，保留实际发言者 |
| 本轮输入 | 完整保留且只插入一次 |

公共背景设明确预算上限，聊天历史使用剩余可用预算；具体默认数值在实现时根据实际模型窗口确定。

若主剧情尚无摘要，可以使用预算内近期完整轮次。发起聊天不顺便触发并持久化一轮主剧情摘要，避免增加一次额外调用和跨聊天摘要写入。

### 7.2 避免公共背景重复积累

聊天摘要只总结本聊天中说过的内容、约定、未决问题和必要的对话关系。

公共背景每轮重新读取，不把整份公共剧情反复复制进每个聊天摘要。聊天中实际讨论过的公共事件可以作为聊天内容保留，但不能将完整公共背景当作摘要输入的历史覆盖范围。

### 7.3 摘要归属与有效性

- 先确定有效历史，再按 chat 选择并压缩。
- 摘要必须带聊天归属与覆盖边界，来源校验包含当前使用的消息内容及发言身份。
- 不复用其他 chat 的摘要；若未来引入不同可见范围，其范围也必须参与有效性验证。
- “被总结历史的末条”与“持久化的追加前驱”分开。
- 保存聊天摘要仍接整局真实 session tip，并归属当前已受理 run 和 chat。
- 公共主剧情摘要在聊天构建中只读。

## 8. 私聊与群聊的生成方式

### 8.1 首版统一调用流程

- 私聊由当前目标角色回应。
- 群聊由模型根据上下文安排一个或多个允许成员回应。
- 不要求每个群成员每轮都说话。
- 不替玩家决定发言或行动。
- 群聊首版不引入每角色独立 Agent、自主循环或并行模型调用。

### 8.2 单 assistant entry 内的多角色发言

保留一次 run 对应一条 assistant entry 的基本执行身份，内部以结构化片段表示角色发言。

以下仅表示领域语义，不是现有 API；实际存储字段和模型输出协议需在实施时一起定稿：

~~~json
{
  "role": "assistant",
  "chatId": "chat-investigation",
  "segments": [
    {"characterId": "alice", "content": "我去看看西侧房间。"},
    {"characterId": "bob", "content": "那我留在这里等你们。"}
  ]
}
~~~

约束：

- LLM role 保持 user/assistant，角色身份使用稳定 characterId。
- 不通过“姓名：”等正文模式猜测身份。
- 发言者必须属于本次允许成员。
- 流式投影能识别当前发言片段，UI 按片段显示气泡。
- 持久化回放、模型历史和摘要均保留发言身份及顺序。
- 整条 assistant entry 是首版编辑、重生成和状态结算单位。
- 若启用状态更新，在整轮回复后统一处理，不让每个气泡独立结算。
- 后续需要独立角色认知或独立决策时，再评估逐角色构建与调用。

## 9. 世界状态、顺序与重生成

### 9.1 推荐的剧情语义

私聊、群聊默认是当前世界内真实发生的交流，与主剧情属于同一条世界线。

切换聊天只改变交流上下文，不切换世界状态。若聊天明确更新了关系或约定，回主剧情后仍保留这些变化。

### 9.2 历史尾部与状态 tip 分开

当前聊天继续使用整局最新有效状态，不能从该 chat 的最后一条消息恢复旧状态。

~~~ts
chatHistory;       // 当前聊天的上下文历史
sessionTipEntryId; // 整局状态读取和追加位置
~~~

既有 global/session/message 状态作用域沿用当前定义。chat 不新增一份独立世界状态。

### 9.3 聊天的状态更新

推荐默认：

- 聊天轮次不自动推进世界时间、移动人物或切换主场景。
- 只有显式启用聊天状态更新时，才执行相关后处理。
- 创作者配置适用状态根，服务端通过 allowedRoots 等现有基础校验写入范围。
- 时间、位置等语义不能靠程序猜字段名称。
- allowedRoots 控制写入，不能替代读取可见性。

### 9.4 锁与历史操作

- 继续使用 session 级串行运行锁。
- 用户可切聊天浏览、编辑草稿；同一 session 不同时执行多个写状态的生成。
- 只允许重生成整局最新 run，不能把“当前 chat 最新”当作“整局最新”。
- 不新增按 chat 独立回滚或自动重算后续跨聊天状态的能力。
- 后续开放更早消息的重演时，需单独设计对后续主剧情与其他聊天的影响。

## 10. 角色知情与跨聊天记忆

本方案首先保证聊天原文与摘要的来源边界，不把新增 chatId 等同于完整的角色知情系统。

当前 load、关键词和 when 用于材料激活，不是知情权限。秘密仍可能存在于角色 prompt、世界书或共享状态中。

典型需求：

1. 玩家在 A 私聊中告诉 A 一个秘密。
2. A 进入 A+B 群后仍应记得。
3. B 在被告知前不应知道。

该需求需要带知情范围的跨聊天事实或记忆。后续可结合记忆模块，记录来源聊天、相关角色、知情者与有效范围。

首版：

- 当前 chat 不自动读取其他私聊、群聊原文或摘要。
- 公共上下文包含约定的主剧情背景和适用材料。
- 角色间的更细知情约束仍依赖明确的材料范围和生成规则，不承诺完整独立认知。
- 单模型同时扮演多个角色时，已输入该模型的秘密主要靠其遵守角色约束；严格独立输入应按角色分别构建。
- 不在本期引入完整事实账本、角色知识库或跨群自动转述。

## 11. Host、SSE 与 SDK

### 11.1 状态归属

| 内容 | 归属 |
| --- | --- |
| 玩家、当前世界状态、总用量、运行锁 | session |
| 历史页、分页游标、滚动位置、草稿 | chat |
| 生成目标与流式回复 | 受理时固定的 chat |
| 行动建议 | 绑定发起 chat，按整局新轮次失效 |
| 事件连接 | session 一条 SSE，由 Host 分发 |
| 角色气泡/头像 | 当前 chat |
| 主舞台立绘 | 独立展示能力，普通聊天默认不自动改变 |

### 11.2 运行与恢复

- 一个 SessionWorkspace 持有共享运行事实和单条 SSE。
- 运行、消息、建议等相关事件携带 chatId。
- 共享 state.changed 继续按 scope 同步，不因为切换 chat 创建不同真相。
- 服务端按 chat 查询历史和分页；不能只在 WorldStory 过滤气泡。
- 切换 chat 后，旧请求的分页或帮答结果不覆盖新聊天。
- 当前活跃 run 显示其实际所属 chat，切换界面不取消或转移运行。
- 刷新后恢复当前聊天历史，同时读取整局活动运行状态。

### 11.3 AI 帮答

帮答继续作为独立用途和预设类型。其材料选择需要识别当前 chat，使用相同的公共背景与当前聊天来源。

帮答草稿绑定原 chat 和请求身份，晚到结果不能写进另一个聊天的输入框。

### 11.4 行动建议

沿用“新一轮同步受理成功即失效”的产品规则：

- 任意 chat 新 run 受理后，整局旧建议失效。
- 新建议只归属本次发起 chat。
- 刷新或切回旧 chat 时，不恢复早于整局最新轮次的过时建议。
- 复用现有历史同步与恢复能力，不新增独立恢复框架。

### 11.5 SDK 方向

与待实施的作者 SDK 治理方案保持一致：

- Host 负责真实运行状态、查询范围、去重和恢复。
- frame/作者组件消费当前聊天的投影和命令能力。
- 不为 main/direct/group 复制三套 Session、History、Snapshot hooks。
- 不由作者组件自行拼接跨聊天模型上下文。
- 聊天选择与创建能力作为小范围入口补充，具体公开 API 在统一 SDK 契约中定稿。

## 12. 服务端组织与复用

新增 prepareChatContext 和聊天执行入口。它们复用基础能力，但不调用“先完整构建叙事，再替换主提示”的流程。

复用：

- 模块公开的世界、角色、状态、历史读取。
- 模板语法和变量展开。
- token 估算与模型预算。
- 历史投影、摘要模型调用等基础工具。
- 模型适配、会话锁、消息持久化、SSE 基础设施。

独立：

- chat 类型节点校验、编排与变量范围。
- 公共背景和当前聊天的组合。
- 参与成员和发言身份约束。
- 聊天输出协议、流式投影和选用后处理。

保持项目既有分层：

- 路由处理传输；业务规则在 Service。
- chat 表和 entries 由 sessions 模块管理。
- 跨模块写流程与提交后事件由 usecases 编排。
- context 负责构建请求，不反向依赖 SSE 或其他执行用例。
- StateService 保持计算职责；持久化由表属主 Service 完成。
- 不为本次需求引入通用 runtime、执行图或 Agent 框架。

## 13. 首版范围与后续能力

### 13.1 推荐首版

1. session 内 main/direct/group chat。
2. 聊天归属贯穿 entries、运行、查询、摘要和事件。
3. 独立 chat 预设类型、官方默认、应用默认及 session 绑定。
4. 公共主剧情背景与当前聊天上下文共同参与生成。
5. 私聊、群聊共用类型与一套对话执行流程。
6. 群聊单次调用、单 assistant entry 内多角色发言。
7. 全局状态链、session 锁和整局最新 run 重生成规则。
8. 聊天历史、草稿、帮答、建议和刷新恢复。
9. 固定群成员、普通聊天头像气泡展示。

### 13.2 后续能力

- 单个 chat 覆盖预设与模型。
- 群成员动态加入、退出及入群前历史策略。
- 严格角色知情范围和跨聊天长期记忆。
- 每角色独立调用、主动发言与自主调度。
- 跨聊天更早轮次的重生成和状态重演。
- 跨群自动转述、完整事实/知识系统。

## 15. 实施顺序与验收重点

### 15.1 建议顺序

1. 定稿 Chat、归属、chat 预设与输出语义契约。
2. 实现表结构、已有数据归入 main、默认聊天预设与绑定。
3. 构建公共背景与当前聊天双来源 context，明确摘要与预算边界。
4. 实现聊天执行、结构化发言、持久化和事件。
5. 接入 Host、UI、SDK、草稿、帮答与恢复。
6. 用函数级测试及项目既有检查验证关键行为，更新对应正式契约文档。

### 15.2 核心验收

- 已有会话迁移后主剧情与状态保持连续。
- 所有新 run、entry、摘要和事件有一致聊天归属。
- 每个私聊、群聊同时拥有公共背景和自身历史。
- A 私聊原文与摘要不会自动进入 B 私聊或另一群聊。
- 公共剧情作为背景注入，当前对话角色与用户输入位置正确，输入不重复。
- 聊天摘要不复制整份公共背景、不覆盖其他聊天摘要，并接整局真实 tip。
- 从旧聊天继续时使用整局当前状态。
- 独立 chat 预设可正常编辑、导入导出；默认配置开箱可用。
- 更换应用默认不替换已有 session 的绑定；更换会话聊天预设作用于后续聊天生成。
- 群聊只允许当前成员发言，发言身份在流式、持久化、历史和摘要中一致。
- 切换聊天不转移正在运行的回复，不串分页、草稿或帮答结果。
- 建议在整局新 run 受理时失效，新结果仅归属发起 chat。
- 某聊天的局部最新回复不是整局最新时，重生成按现有规则拒绝。
- 对话能力不意外继承叙事主提示、立绘或其他未启用后处理。

## 16. 实施前仍需定稿的细节

以下局部细节不影响本方案主要架构，在正式实施时确定：

- chat 输出的精确线协议、segments 的最终存储字段与流式事件形式。
- 聊天与公共背景的默认预算、聊天摘要提示词和历史保留参数。
- 聊天首版需要默认开启哪些可选能力，以及允许更新的状态根配置入口。
- chat 管理、发送和查询的最终路由与 SDK 命名，需与待实施的 SDK 治理方案协调。

这些细节应在实现前形成可验证契约；不通过复用完整叙事流程隐式决定。
