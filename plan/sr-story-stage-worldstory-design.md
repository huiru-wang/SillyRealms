# 故事舞台与新版 SR.WorldStory：阅读界面设计

> 当前状态：2026-11-14 按首轮交付后的反馈完成消息左右边界与 Studio 玻璃输入调整。界面实现完成，Studio/Web 构建与最新生产 Studio 会话全套通过；补充 Web 字号专项 7/8 通过，原生 End 返回底部/恢复跟随未稳定通过，保留为未解决验证项，不宣称全部门禁通过。第 10 节为首轮历史，本轮证据见第 11 节；用户视觉认可与真实 Server 会话接入分别验收。

## 1. 目标和范围

用户进入会话后，能够快速辨认自己的输入与 AI 叙事，并持续阅读较长正文。用户消息靠右、宽度较窄，AI 叙事靠左、阅读面较宽；两者以克制的底色、细边界、来源标签和段距分隔，减少连续无边界正文带来的阅读疲劳。此口径来自首轮交付后的明确反馈，覆盖原稿“完全无气泡、无外框、同一左轴”的要求。

原稿的设计范围为：官方 `SR.WorldStory` 默认展示、会话页 Host 输入框的视觉与交互，以及 Studio 接入后两者的视觉衔接。历史分页、实时消息、恢复、消息规则和组件、会话状态、发送/停止等既有能力按当前实现保留，不设计新功能、不改动数据协议和运行逻辑。暂时移除输入区中“话语”“系统指令/叙事指令”快捷按钮；这是入口展示调整，不删除语法、历史内容或已有消息渲染行为，也不推断禁止手工输入。执行时已核对现有编辑器键盘、粘贴和序列化行为；不以静默改写用户输入代替取消按钮。

## 2. 术语与边界

- **会话页**：平台外壳，负责标题、返回、上下文用量、连接状态、设置及 Host 输入框。移动端会话详情不显示全局底部导航。
- **故事舞台（Story Stage）**：世界卡决定内容与布局的区域，可能是官方默认界面或作者自定义 UI。
- **`SR.WorldStory`**：官方默认故事组件，也可由作者在自定义舞台内组合。它与自定义舞台使用同一公开 SDK 契约；不是会话页或整个舞台的同义词。
- **消息边界**：保持当前消息身份、顺序及可访问的来源标识；沿用已有相邻 assistant 消息的展示合并规则，不要求将原始消息一一渲染成视觉块，也不把所有历史拼为一个无身份长字符串。展示不改写原始消息或状态。

当前 SDK 的 `StoryRun`、`MessageContent`、Run 反馈与建议、状态面板、Host 输入属于已有能力；本方案对它们的布局提出目标，不将重写 reducer、流式协议或状态处理列为设计目标。评估时 Studio 会话样板为静态示例；现已改用真实 SDK 的隔离本地预览，真实 Server 会话接入仍须后续单独验收。

## 3. 页面构图

| 层次 | 位置与布局 |
| --- | --- |
| 平台标题 | 顶部保留标题、返回及必要状态与设置入口 |
| 故事舞台 | 占据有界内容区域，延伸至输入浮层后方；消息在 iframe 内独立滚动 |
| 官方消息 | 居中的阅读列内，AI 叙事靠左且较宽，用户消息靠右且较窄 |
| Host 输入 | 底部悬浮的玻璃表面；左侧收起、中间输入、右侧发送或停止，始终保持同一行结构 |

手机详情不出现全局底部导航。输入区初始只占一行，长文本自然换行并向上增高；达到可用高度上限后在编辑区内部滚动。收起后保留轻量展开入口，舞台继续位于浮层后方。Host 与 iframe 仍通过既有消息边界协作，不跨文档直接读取或操作作者 DOM。

阅读列桌面最大宽约 740 CSS px，随容器收缩；用户消息桌面最大 `min(82%, 580px)`，手机可放宽至 86%。手机叙事保留舒适内距，正文自然左对齐，来源与左右位置共同区分角色。作者外围布局不被强制压入此阅读列。

Host 根据实际浮层高度测量舞台遮挡，经既有 appearance 通道传递并设置 `--sr-story-bottom-inset`。官方阅读区、回到最新、状态面板和受控组合样例留出足够滚动余量，使最后一行与交互控件能够滚至浮层上方；舞台背景仍可从玻璃后方透出。

## 4. 阅读排版与视觉

- 深浅主题沿用 Studio 既有语义色、文本层级、间距和焦点样式。会话 iframe 中的官方组件使用经明确映射的阅读变量；平台样式不能全局注入或强制覆盖作者自定义舞台。无论主题，正文、次级信息、状态和焦点都须满足对比度及可辨识要求。
- 正文以常规字重、清晰段距呈现；初始目标约 16px、行高 1.8–1.9，手机可根据可读性微调。沿用现有阅读字号设置及其作用范围，不额外发明存储策略。长单词和 URL 换行；代码与表格可局部横向滚动；图片限制容器宽度、保持比例，并在加载和失败时保留合理阅读位置。
- 用户消息位于阅读列右侧，AI 叙事位于左侧；正文始终自然左对齐。来源标识小于正文，用户为“我”，AI 在没有可靠角色名时使用“故事”，不根据正文猜测角色或制造头像。左右位置、文字来源和表面边界共同表达身份。
- 同一 AI 消息中段落间距小于消息之间的间距。AI 使用较宽的极淡表面和细边线，用户使用较窄的浅强调色表面；避免厚重阴影与高对比卡片堆叠。保留换行、文本选择、作者内容及组件边界，触控、键盘和辅助技术均能识别消息顺序。
- 空故事、正在加载、加载失败、重新加载更早内容、准备/生成/扩展处理、停止、失败及连接问题沿用实际状态；反馈紧邻相关区域，错误含现有重试入口。未保存的流式内容仍是暂态，终态以权威结果为准；不要虚构持久化、断线重放或保证。
- 行动建议保留最新可用、历史禁用和只填草稿不自动发送的语义。Studio 填入后直接反映在输入内容中，不显示“已填入草稿／撤销”等通知，也不保留这套独立撤销提示状态；Lexical HistoryPlugin 和编辑器键盘撤销保留，正式 Web 的独立 setDraft 撤销 UI 不在本轮调整范围。

## 5. 文本渲染保持不变

官方组件继续调用现有 `MessageContent` 渲染 AI 与用户消息：保留现有角色扮演文本处理、用户指令段的处理、Markdown 与 HTML 混排、净化、安全链接、世界卡消息展示规则、作者消息组件和 React Portal 插槽；不把消息直接改成纯文本、静态 iframe 或 `dangerouslySetInnerHTML` 快捷实现。用户消息和 AI 消息既有处理细节不同，以当前代码和测试为准，不将它们误说成完全同一种解析流程。

作者内容内的结构、链接、代码、样式和交互按现有安全约束呈现，平台只定义外层阅读节奏；不通过 CSS 全局覆盖作者组件。规则超时、组件缺失或局部异常时维持当前原文回退及提示。自定义页面失败继续按既有错误规则处理，不擅自换成默认舞台。`showState` 的现有默认值与功能保持；桌面、移动端面板布局和焦点沿现有语义实现。

## 6. 简洁输入区

输入区属于 Host。展开时仅有一行结构：左侧收起按钮、中间编辑器、右侧发送按钮；运行中右侧切换为停止。删除顶部标题、快捷键解释、独立 footer 和发送成功提示，placeholder 统一为“写下你的回应…”。实际发送失败保持可见，输入和按钮仍有可访问名称及焦点样式。

浮层参考 Studio 移动导航的玻璃材质，使用半透明背景、backdrop blur、饱和度与细微边缘高光；没有额外不透明底带挡住舞台。深浅主题分别适配，减少透明度偏好及不支持 backdrop-filter 时使用可读的实色回退。文本自然换行增高，按钮保持在两侧。ResizeObserver 根据舞台可用高度和实际错误提示、边距等非编辑区高度，按 96px 舞台预留预算计算编辑空间，编辑区最小 44px；超长草稿在内部滚动。错误块另有随可用视口变化的高度上限，避免短视口下挤占状态 dialog 的关闭操作。

复用现有 `RoleplayComposer` 四 props 接口与 Lexical，保留语义节点、HistoryPlugin、IME、粘贴、序列化及长度限制。普通 Enter/Shift+Enter 换行，Cmd/Ctrl+Enter 发送，已有语义块内 Enter 退出到旁白。Studio 去掉独立 setDraft 撤销提示状态，继续保留 pending 与 draftRevision 保护：运行中可编辑下一份草稿，迟到的发送响应只清理对应未变更版本，拒绝发送保留草稿。

遮挡高度随输入增长、收起展开和可见视口变化重新测量，通过受限 appearance 消息传入 frame；不新增公开业务 SDK、不放宽 iframe sandbox、CSP 或来源校验。真实软键盘仍需独立验证，桌面缩小视口仅用于检查可达性。

## 7. 滚动、状态与无障碍

- 沿用现有历史分页、位置锚定、用户上翻停止跟随、回到最新及图片/组件高度变化处理；视觉变更不得重新挂载历史消息或 Portal 插槽。没有虚拟列表或可重放 SSE 的既有保证。
- 桌面状态面板展开不挤压正文至不可读，状态内容底部包含浮层避让留白。窄屏原生 dialog 的底部与高度直接避让遮挡，其内部不重复增加同一留白；焦点管理和关闭后返回沿现有契约。`showState=false` 不显示官方状态入口或面板。
- 来源、错误、状态、操作的含义不能只靠颜色。阅读区可用键盘，交互控件有名称和可见焦点，移动触控目标建议至少 44px；尊重减少动态效果。滚动到新消息不能夺取焦点或让屏幕阅读器重复朗读整段历史。
- 等待和断线文案不提供超出现有接口的“已同步”承诺；空态、错误和重试均保持可读，刷新失败不能伪造空故事。

## 8. 接入与验证范围

首轮已在隔离测试环境中以固定合成数据和现有 SDK/Host 契约展示默认及作者组合两种场景。本轮沿用该接入边界，无需真实 Provider、真实用户会话或付费调用；不得绕过 Host、MessageChannel、iframe sandbox、CSP 和公共 SDK。样式和布局避让只影响呈现，不改变业务协议或数据库。

视觉验收：1536、1280、768、390、375、320px，深浅主题；检查短/长中英文、长用户消息、混排、代码、表格、图片、组件及错误回退。重点检查消息左右位置与边界、输入单行初态及自动增高、舞台在玻璃后方滚动、缩短视口时操作可达、最后一行与状态面板避让。本轮实际完成的浏览器与截图检查见第 11 节，真实软键盘仍不由桌面视口模拟替代。

交互回归：历史分页与锚点、滚动跟随与回到最新、流式阶段和终态、图片异步布局、规则及组件插槽稳定、失败和重试、状态面板、建议与草稿、输入法/快捷键、切换会话与取消、窄屏横向溢出、触控与键盘焦点、减少动态效果。运行 Studio 构建和对应 SDK/Host 浏览器测试；截图或测试未运行时明确报告，不能宣称视觉通过。

## 9. 首轮实施顺序与授权（历史）

1. 确认消息来源标签、文本尺度和输入快捷键基线，建立固定合成样本与现有行为基线。
2. 分别确定 Host 会话页与 SDK 默认故事的视觉边界，明确 iframe 内主题变量和作者组合兼容方式。
3. 只调整官方消息外层排版与状态面板外观，保留 `MessageContent`、消息身份、合并和运行反馈。
4. 在 Host 侧简化输入外观，移除两个快捷入口并验证原文本格式、草稿和发送行为。
5. 在 Studio 的隔离预览接入真实 SDK/Host 契约，分别验证默认舞台与作者组合场景；不在本阶段承诺服务端真实会话接入。
6. 按第 8 节检查跨端视觉、安全和回归，记录差异及未验证项；通过评审后再更新正式实现文档。

原设计稿本身不授权实现或上线；用户随后已明确要求执行方案并在完成后提交推送。本期按该授权实施与同步文档，交付范围仍限于 SDK/Host 展示和本地隔离预览。
