# 《灭仇家满门之后，我收养了想对我复仇的孤女》转换方案

依据高松特灯灯的 2.4.5 版角色卡及当前仓库的世界卡契约。以下是对内嵌数据和源码的静态解析，以及在 SillyRealms 中重建玩法的设计。

## 原卡解析路径

1. **核对容器与有效载荷。** 解码原 PNG 的 `chara` 与 `ccv3`，两者的 `data` 相同。常规人物描述、性格、场景均为空。实际入口是 HTML 首条消息、71 条世界书、6 条正则和 5 个助手脚本。世界书出厂启用 44 条。示例消息中的不透明注释不作为剧情正文。
2. **从操作追到第一幕。** 首页七页依次承载说明、选局、配置和人物创建。只有“黎氏灭门之后”可选。开局保存三选一难度、可并选的仙侠与志怪、玩家自填人设和五道“这些年”问答，再写入黎安于南下马车醒来的定稿。未选难度回落到普通。世界书的开场示范用于补缺，有定稿时首轮接玩家行动。
3. **分别写出世界事实和人物认知。** 1878 年的大顺势微，朝廷难制武林，暗中向杀手组织“仇”买下灭黎家的生意。玩家是天榜第三，也是十年前被黎家灭门的幸存者；开局默认二十二岁。十三岁的黎安知道玩家参与灭门，尚不知私仇与买家的内情。江南无锡的日常、学艺与外出游历不断给两人制造选择。裹面娘子与组织使后期的去留有了具体代价。
4. **沿一轮游玩读状态。** 从初始变量、Zod、MVU 更新规则读到面板消费方，核对时间与历法、双方年龄和各自地点、修为武学、衣物物品、天气、已发生与进行中事件。黎安的恨仇、依恋、撕扯、怀疑、悔意可以并存。她想独立闯出名堂，每个行动怎样改变她的判断，要结合她亲历的事。已揭真相只收录正文里她实际获知的项目。
5. **逐项还原触发条件。** 将初来、学艺、及笄、同行、未来五阶段，与单选且可关闭的九条线路分别追踪。与黎安同行有归隐、江湖、嫁衣；选择组织有叛离、病娇、遥游、堕魔；异路有误解、复仇。另有自定义线路。六个爆发点分别为私仇真相、买家朝廷、灭门丑态、黎家原罪、自欺、组织变故。逐一厘清开放素材、情节发生、谁已确认。进入“未来”还要求组织变故后确有分别或下落、生死未明，原面板的按年龄选择会在此处请求确认。
6. **核对世界书的内容来源和加载入口。** 常驻材料管时代、扮演与信息差；八个大区和无锡专条、组织、修炼与地煞术法、人物速写、武学生成、各色语料按需生效。描写重心、玩家偏好、难度、要素由设置控制。十五个节日由本局剧情日历或手选项触发专用扫描键。原历表支持 1878—1978 年，公农历冲突时暂停自动触发。
7. **按真实副作用拆正则和脚本。** 六条正则中，两条从模型输入隐藏占位符或变量块，两条美化流式和完整变量块，旧状态栏替换与隐藏首页默认关闭。五个脚本中，MVU 加载器、Zod、气泡面板、更新与存档启用，独立旧状态栏关闭。面板还承担修数、人设编辑、地图地点编辑、世界书切换和自定义线路。本期制作首页与手札中的游玩操作。

## SillyRealms 构建方法

| 顺序 | 建设对象 | 落点与验收依据 |
| --- | --- | --- |
| 1 | 角色和知识边界 | 在 `characters` 建立一个可扮演的天榜第三和常驻 NPC 黎安。玩家可自定民间身份，黎安保有行动目标、五色反应与年龄边界。裹面娘子等关键人物按需加载，市井路人沿用地域生成规则。详情介绍采用无剧透视角，模型材料显式标出各方知情范围。 |
| 2 | 开局和建角 | `openings` 只收录定稿马车开场，`initial_state` 提供完整的消息根初值。首条可用第二人称“你”，让玩家随后填写的别名也能成立。介绍和预览只展示内容；把身份表、难度、要素和五问放到会话舞台、首轮行动之前，确认保存成功后接续第一幕。仅允许编辑本局。 |
| 3 | 状态和提示词 | 用 State V2 的 `message` 保存剧情事实、双方动态资料、五色、已揭事实和事件。每个根、容器与叶子写明更新依据。玩家控制的难度、要素、线路及手动覆盖项放在 `session`，通过 `load.when` 选择对应的模型材料。需要模型直接阅读的自填人设或自定义线路正文放入本轮可见的消息状态；自由文本与玩家选择的设置各有明确写入者。 |
| 4 | 世界书和触发规则 | 把 71 条逐条映射为人物、开局、状态定义、常驻规则、关键词材料或受状态控制的材料。保留地域别名和语料用途；仙侠、志怪开关分别控制原卡对应的指引；修炼、术法、地域条目沿用各自的关键词和开关。六个爆发点分别保留可用开关与知情记录。九条线路同时核对选择和情节前提；五阶段出厂全关；玩家点击“按年龄自动”时才读取年龄，并在组织变故后核实去留。 |
| 5 | 地图与日历 | 提取坤舆图、城市和地点资料，地图浏览保持只读，玩家自订地点另存为本局补充；叙事移动后分别更新双方所在地。将十五个节日的自动日期命中和手动选择编为可供服务端读取的条件，保留历表范围和公农历一致性校验。验收时覆盖仅提到节名、手动指定、日期不一致三种情形。 |
| 6 | 舞台与消息展示 | 在 `stage_component` 复用官方故事流，通过 SDK 接入状态、武学、地图、线路、阶段和设置；修数后读取服务端实际值。正文交给平台叙事链，旧 JSON Patch、状态栏占位符与正则美化由原生状态后处理和面板承接。只有确有正文展示需求才增加 `message_render`。 |
| 7 | 打包与回归 | 采用根 `world.json` 加 `components/`、`assets/` 的 ZIP，保留作者、来源及“禁止商用、二次创作注明出处”的原卡说明。按任务清单做导入器、上下文、状态与组件的函数级验证。验收对象为本卡的新局游玩。 |

目标契约见 [世界卡样例](../examples/worlds/fog-harbor/world.json)、[世界卡组件](../docs/design/world-components.md)、[状态 V2](../docs/runtime/state-v2.md)、[叙事运行](../docs/runtime/server-narrative.md) 与 [素材选择实现](../apps/server/src/usecases/context/stages/materials/index.ts)。

## 实施顺序与验收证据

### 原卡第 0 条消息与自定义开局舞台

原卡的 `first_mes` 是角色发出的第一条消息，其内容为七页可交互 HTML。玩家翻页、设置难度、填人设、完成五问后，按钮按填写的姓名组装作者定稿，再用 `setChatMessages` 把第 0 条消息替换成马车正文。替换不可用或失败时，原卡尝试追加一条 assistant 消息。整个按钮流程无需模型生成。原文来自本地资料 `resources/silly-tavern/灭仇家满门之后，我收养了想对我复仇的孤女/原始资料/首页.html.txt`，不随仓库发布。

在 SillyRealms 使用世界卡自己的 `stage_component` 作为会话入口，按以下顺序呈现。

1. 服务端创建会话时保存唯一的马车开场及初始状态。世界卡声明 session 布尔根 `建角完成`，初值为 false。开场正文沿用原卡未填姓名时的“你”。
2. 舞台通过 `useSRStageSnapshot()` 读取会话状态。状态加载期间等待读取结果，读取出错时呈现重试。明确读到 false 时只挂载七页开局组件。详情页的开局预览只承担展示。
3. 玩家点击“完成，开始”，组件通过 `useSRStateAPI()` 提交难度、要素和模型可见的人设、问答结果、初始人物字段，按写入结果与实际值核对。全部确认后再把 `建角完成` 写为 true；失败时保留当前页与填写内容。提交用最终值覆盖，重复点击也只对应服务端已有的那条开场。
4. 舞台读到 true 后挂载 `SR.WorldStory` 与江湖手札。玩家看到马车正文，接下来由玩家行动推动第一轮叙事。原卡可在马车定稿中使用刚填写的名字；本方案中保存的第一条正文称“你”，自填名从后续叙事生效。
5. 宿主页面在舞台 iframe 外还渲染了消息输入框。现有组件 API 能切换舞台内容，宿主发送按钮仍按自己的条件启用。若要求“未建角时任何入口都禁止发送”，需单独设计宿主与服务端的提交约束。本次世界卡按现有能力规划。

实现依据见 [会话创建](../apps/server/src/usecases/create-session.ts)、[舞台状态 API](../packages/sr-sdk/src/stage/runtime.ts) 和 [宿主会话输入框](../apps/web/src/features/sessions/SessionPage.tsx)。

| 原卡行为 | 本卡的判定方法 |
| --- | --- |
| 来源与依赖 | 以 PNG 哈希、世界书 ID、脚本名称或首页处理函数定位原件。截图只证明所见界面。酒馆助手承载脚本，MVU 加载器引用外部实现，Zod 脚本注册模式。实际安装版本、外部库就绪和每轮提示词有待原环境记录；每项标明证据来自卡内、截图、运行记录还是推断。 |
| 世界书与人物 | 对每条保留默认开关、触发词、顺序、位置、作用对象和迁移落点。比较相同输入下实际选中的材料与下一次模型请求。单独核验黎安、玩家、折桂和温半壶的在场、责任与知情边界。核心常驻概览、可选演出、已揭记录分别核对。 |
| 状态与编辑 | 给字段记录初值、作用域、写入者、写入时机、消费者、下一轮是否可见。原卡写入绑定世界书的玩家设置改为本局隔离，属于体验差异。对手札修数、文本编辑、自定义地图／路线都做“保存、读回、下一轮取材”验证。State V2 的 JSON 嵌套规则是说明文字，原 Zod 的强制夹限、集合增删需单独对照受支持的根类型或整根更新。 |
| 自动节日 | 原历表中 1878 年 9 月 11 日对应八月十五。自动模式下，这天的下一轮应能取到已启用的中秋风物；平日谈论“去年中秋”应不命中。若公农历矛盾则暂停自动选节，手动模式按本局勾选。用实际素材选择结果核对。当轮可取用相关风物即可，正文是否描写由场景决定。目标端日期换算与材料选择的衔接需实现验证，服务端的 `load.when` 不能直接执行原历法脚本。 |
| UI | 用现有第 4 页截图对齐纸色、书页层次、章号、单个可选项、两个锁定项和返回操作。其余六页、地图缩放和手札六页按源码还原，在窄屏与桌面宽度检查可读、滚动、返回、保存与失败重试。有同视图参照时并排比对，缺原图的视图标明证据级别。 |

### 本卡的完成条件

从七页开局玩到第一轮行动，再以地域移动、节日、真相揭晓和阶段选择核验后续游玩。对照三类实际结果：玩家在界面上看到什么、服务器保存了什么、下一轮模型取得哪些人物与世界书材料。按剧情与人物、状态与取材、UI 与操作记录结果。
