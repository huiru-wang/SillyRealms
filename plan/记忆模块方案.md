状态：**建议方案，待实施。本次只新增计划文档，不修改业务代码。**

日期：2026-11-23  
项目：SillyRealms  
核对基线：当前代码 HEAD d250d23。  
目标：以长期产品职责为依据确定记忆设计；现有代码用于核实产品事实和实施落点，不作为限制设计的理由。

## 1. 推荐结论

采用 **独立记忆模块 + 世界卡定义内容规则 + 预设提供运行默认值 + 会话决定实际启停 + 消息关联来源与版本**。

日常记忆首先服务于一条会话中的持续叙事。它保存值得日后使用的经历、信息和关系背景，并在需要时取出相关部分。模块独立拥有数据和生命周期，但不需要先实现第三方插件市场、单独进程或独立数据库服务。

| 用户提出的方向 | 建议结论 | 必须补充的边界 |
|---|---|---|
| 独立模块，关联世界、会话、消息 | 赞同 | 世界关联、会话归属、消息来源不是三个互斥的 scope |
| 通用结构，不预定义业务记忆类型 | 赞同 | 平台仍固定 ID、内容、归属、来源、版本等公共字段；业务分类由世界定义 |
| 世界卡定义类型、召回策略、抽取提示词 | 赞同 | 策略必须是平台能执行的规则；自然语言不能改变写入权限或数据协议 |
| 预设子模块或提示词编排条目 | 两者配合 | 子模块控制运行；编排节点控制放置位置；会话只有一个真正的总开关 |
| 默认开启，可以关闭 | 新会话默认开启，会话可独立关闭 | 关闭保留数据；已有历史补抽与开关分开；暂停后继续过剧情需补齐缺口 |
| 同回合输出记忆数据块 | 作为首版默认 | 使用叙事模型；另选抽取模型必须是额外调用 |
| 数组增删还是整体替换 | 稳定 ID 的 add / update / remove | update 替换单条内容；正常回合不允许整体替换记忆库 |
| 世界卡详情查询相关记忆 | 支持 | 按会话区分；集中查阅不等于跨会话自动共享 |
| 任意楼层修改、删除 | 必须进入首版正确性边界 | 最新回合可撤回；中间历史变化会使后续自动记忆待整理 |

最重要的设计要求是：**能够判断当前记忆对应哪一份有效剧情，并在剧情被改动后停止使用过期结果。** 向量检索、独立抽取模型可以逐步增加，这条边界不能后补。

## 3. 会话级、消息级和世界级究竟是什么关系

### 3.1 分开回答三个问题

| 维度 | 回答的问题 | 首版语义 |
|---|---|---|
| 世界关联 | 这条记忆在哪个世界下产生，使用哪套类型定义？ | worldId，用于定义关联、筛选和生命周期管理 |
| 会话归属 | 哪条故事线可以读取、更新它？ | sessionId，默认仅所属会话可自动读写 |
| 消息来源与版本 | 哪段正文产生它，在哪个剧情位置发生变化？ | 来源消息及其内容版本、记忆变更的锚点 |

同一条记忆同时具有这些关联。例如“林舟曾把母亲留下的铜钥匙托付给玩家”属于某个世界下的会话 A，来源于 A 的一轮对话。它可以在世界详情被查到，但不能因此成为会话 B 已经发生的事实。

**不建议把 message 做成与 session 并列、互斥的记忆拥有者。** 首版对用户可以直接叫“会话记忆”，把来源楼层作为记录的属性展示。

真正的“世界共享记忆”意味着多条故事线共同承认某个事实，是额外产品能力。未来可从用户主动发布共享事实开始；普通对话模型默认不能向其他会话写入。平台静态世界设定继续放在世界卡、世界书，不借“共享记忆”重复一份。

### 3.2 最新消息记忆是不是会话记忆

**在当前内容视图上，是；在归属与历史管理上，是同一份数据的不同维度。**

例如：

| 剧情位置 | 本轮变更 | 当时累计有效记忆 |
|---|---|---|
| 第 10 楼 | 新增“林舟请玩家替他保守身世秘密” | A |
| 第 11 楼 | 无变化 | A |
| 第 12 楼 | 更新为“玩家已向船长透露林舟的身世” | A 的新版本 |

第 12 楼的累计视图就是当前会话使用的记忆。消息关联让系统知道：删掉第 12 楼应撤销哪次更新；重新生成第 12 楼时不能沿用旧结果；改掉第 10 楼时哪些后续结果需要重新判断。

因此不维护一套“会话记忆”再加一套内容重复的“消息记忆”。应维护：

1. 当前有效记忆集合。
2. 记忆条目的必要历史版本与变更来源。
3. 已处理的历史范围、尚待整理的位置。

### 3.3 不在每条消息上复制全部记忆

推荐每轮只保存变更及其来源，无变化的轮次沿用已有记忆版本。消息只关联本次处理记录；记忆正文由独立模块管理。

当前有效视图可以单独维护以便查询，但它是同一批版本记录的当前投影，不是另一份可独立修改的事实库。必要时再增加稀疏检查点优化读取，不把“每层一份全量副本”作为产品要求，也不为此建设通用事件溯源框架。

历史查看还要区分：

- **当时提取的记忆**：保留当时实际处理的记录。
- **按当前正文重新整理后的记忆**：表示现在应该记住的内容。

重新整理当前记忆，不等于重新模拟并生成每一楼当时应该有的记忆；首版不承诺这一点。

## 4. 记忆与状态、摘要的边界

二者在回合内生成数据块、校验、保存、查看和修正的流程上相像是合理的。但它们回答不同的问题。

| 能力 | 核心问题 | 数据特点 | 用法 |
|---|---|---|---|
| 世界卡 / 世界书 | 世界的既定设定是什么？ | 作者提供的背景和规则 | 按世界材料规则载入 |
| 状态 | 现在是什么？ | 预先声明的结构、当前值、精确读写路径 | 作为当前有效值使用 |
| 记忆 | 发生过什么，哪些信息值得以后使用？ | 随剧情增长的条目、来源和意义 | 按相关性与预算选择一部分 |
| 历史摘要 | 被压缩的那段对话整体讲了什么？ | 某段历史的连续概括 | 配合近期原文维持剧情连贯 |

### 钥匙例子

- “玩家当前是否持有铜钥匙”：如果世界定义了背包状态，应由状态负责。
- “林舟把母亲遗物托付给玩家，并请他保密”：适合记忆。
- “前二十轮从酒馆争执到码头会面的经过”：属于摘要。

记忆不再维护一份与背包状态竞争的“当前物品数量”。对同一已声明字段，**当前有效状态负责当前值**；记忆中的历史表述需要保留发生时间和原因，不能反过来无声覆盖状态。

这也不意味着状态永远语义正确。用户改了旧正文后，现有状态可能需要手动纠正或主动状态更新；记忆整理不负责替状态重算。发现“正文、记忆、当前状态”冲突时，不能把整理完成展示成整个故事已经一致。

### 多角色叙事的补充

首版是供叙事模型使用的会话记忆，不是每个 NPC 各有一套独立 Agent 记忆。记录应保留“谁知道、谁声称、何时发生”的语义：

- “林舟声称仓库无人看守”不能直接变成“仓库确实无人看守”。
- 叙事模型知道一个秘密，不等于每个角色都已获知。
- 用户的计划、假设、行动建议不能直接当成已发生结果。

这些要求先进入默认抽取与使用规则。若以后需要严格的角色知情隔离，再增加明确的可见性字段与召回限制，不能只靠一句提示词声称已经实现强隔离。

## 5. 通用持久化结构

“不硬编码业务类型”不等于“没有结构”。首版使用以下公共概念即可。

| 信息 | 用途 | 来源 |
|---|---|---|
| 稳定记忆 ID | 后续精确更新、移除、追溯 | 平台生成 |
| 世界关联、会话归属 | 查询与故事隔离 | 服务端依据当前上下文绑定 |
| 类型 ID | 引用世界定义的业务类别，可为空表示通用记录 | 世界定义 / 平台通用兜底 |
| 记忆正文 | 可读、可注入模型的一段明确陈述 | 模型提取或人工维护 |
| 关键词 / 关联对象 | 支持首版相关匹配与筛选 | 可选提取；已有对象引用应使用真实 ID |
| 来源与变更锚点 | 关联普通消息、来源内容版本和覆盖区间 | 平台记录，模型不得任意伪造 |
| 版本与有效性 | 当前有效、已撤下、来源变化待整理 | 模块管理 |
| 人工修正 / 置顶标记 | 防止无声覆盖，控制展示与优先级 | 用户操作 |

正文优先用文本，不要求每个作者再定义一套任意 JSON Schema。来源、关键词等公共字段帮助管理；不要把记忆做成第二套可任意修改状态树。

持久化分工如下，每项只有一个写入属主：

1. **会话有效配置**：会话模块唯一保存实际开关、策略及默认值来源。记忆模块读取生效配置，不再持有另一份可独立修改的副本。
2. **覆盖信息**：记忆模块保存开始维护的位置、处理到哪里、是否存在历史缺口、待整理的最早位置。即使始终没有提取出条目，也需要这份信息。
3. **记忆条目及版本**：记忆模块保存稳定 ID、正文、类型、有效性、来源与人工维护标记。
4. **回合处理记录**：记忆模块保存本轮新增、更新、移除的结果及对应消息，用于撤销、查询和诊断；使用过的配置版本仅作处理依据记录。
5. **当前有效视图**：记忆模块管理当前应参与召回的条目，必须与上述版本和有效性一致。

“没有产生新记忆”和“没有成功处理这一轮”必须可区分。正常无变化仍记录已处理；失败、取消、缺口不能靠最后更新时间伪装成全部历史已覆盖。

消息里的处理回执只引用处理结果和记忆 ID，不再复制完整长期记忆库。普通消息编辑不能伪造记忆处理结果。

## 6. 世界卡：定义记什么与怎样找

### 6.1 每个类型的最小定义

| 配置 | 作用 |
|---|---|
| 稳定 typeId | 改展示名不改变已存记录归属 |
| 名称与说明 | 说明此类内容的业务意义 |
| 抽取规则 / 提示词 | 什么值得记，怎样表达，什么时候更新或撤下 |
| 召回策略 | 常驻优先、关键词/关联对象匹配、近期补充等平台支持的选择 |
| 条数或权重偏好 | 类型内部筛选偏好，仍受会话总预算限制 |
| 可选适用条件 | 在特定情境载入该类型的抽取规则；缺省即适用 |

“约定”“关系转折”“调查线索”等只是世界作者可以创建的例子，不成为平台固定枚举。旧世界卡没有类型定义时，仍可使用未分类的通用记忆与平台默认规则。

首版不要求作者配置复杂条件。默认适用全部类型；明确配置条件时，依据当前输入、近期干净正文与可用状态判断，不因为该类型没有已存记录就停用它的抽取规则。

### 6.2 提示词与执行策略分工

世界提示词描述内容规则；真正的检索方式、预算和写入边界由平台执行。

例如“重要时想起这个秘密”可以作为语义说明，但不能代替可执行召回策略。自然语言也不能授权模型跨会话更新、改写状态、输出另一种不受支持的协议。

类型改名保持 ID。停用类型不销毁旧记录；删除类型后，既有记录保留来源与原类型标识，管理界面标为未定义类型，默认不再自动写入该类型。重新映射或重新整理必须明确执行，不能按相似名称静默合并。

修改抽取规则主要影响之后的处理，不自动改写全部旧记忆。涉及类型含义变化时，应在记忆设置中提供显式的应用与整理入口。

## 7. 预设与会话：运行设置和真正的开关

### 7.1 选择“记忆子模块 + 编排节点”

预设增加与上下文、模型参数、提示词编排同级的“记忆”模块，用于配置：

- 默认是否开启。
- 抽取方式；首版只有同回合抽取。
- 通用抽取提示词，支持恢复平台默认。
- 召回总预算、默认筛选策略。
- 整理提示词的默认值；首版使用会话当前模型。

提示词编排中的记忆节点仅决定召回结果的位置。抽取规则在本轮确实启用抽取时载入。功能开关、抽取条件、已召回的记忆数量是三个不同判断。

**只有一个真正的总开关。** 编排节点反映生效状态，不提供另一个会造成冲突的隐式开关。启用时缺少必要节点，应由规范化补默认位置或在保存时给出明确反馈；不能无声变成“继续抽取但永远读不到”。

底层分开判断读取与更新，便于未来提供只读模式；首版 UI 用一个总开关即可，不强迫用户理解多种模式。

### 7.2 会话应用默认值，避免共享配置强制联动

- 平台与内置预设默认开启；新会话应用所选预设的实际记忆配置，预设显式关闭时继承关闭，用户可在本会话覆盖。保存本会话的有效配置及来源信息。
- 同一预设下的会话可以有不同的记忆开关。
- 调整预设默认值不直接改变所有已有会话；已有会话通过“应用新的记忆设置”更新。
- 切换叙事预设不清空记忆，也不无声替换本会话记忆策略。
- 仅为记忆配置保存必要的有效值，不借此重做全项目的配置继承系统。
- 世界类型使用稳定 ID；某次处理使用的定义/配置版本应可识别，不能用展示名推断语义兼容。

### 7.3 关闭、开启、补齐与清空

| 用户操作 | 结果 |
|---|---|
| 关闭记忆 | 停止自动召回和抽取；即使模型意外返回旧记忆块也不执行；保留数据 |
| 关闭期间没有继续剧情，再开启 | 继续使用仍然有效的记忆 |
| 已开始维护记忆，关闭期间又继续了剧情，再开启 | 标出未处理范围；下一次回复前先补齐该范围，即使此前处理结果一直是零条记忆 |
| 从未启用过的旧会话开启 | 默认从当前轮起记录；不自动扫描全部旧历史 |
| 用户选择“补全已有历史” | 明确范围后进行额外模型处理，完成前不宣称旧历史已记住 |
| 清空记忆 | 单独清除所选会话的记忆数据与历史版本；不删除对话或状态；默认从当前位置重新积累 |

是否补齐暂停期间的缺口，依据维护起点和覆盖记录，不依据当前是否有非空条目。“补全全部旧历史”是另一件事。两者都应说明处理范围，不把一个开关隐含成无限制历史扫描。

关闭只停止自动召回与抽取；此时编辑或删除消息仍登记来源变更，防止再开启时误用旧结果。

已有会话的升级不自动回填历史。旧配置缺少字段时可以补兼容默认，但应在首次使用时显示实际起点；不能把已有对话全部标记成已处理。

### 7.4 同回合模式与独立模型

| 模式 | 使用的模型 | 触发 | 首版 |
|---|---|---|---|
| 同回合抽取 | 当前叙事模型 | 正常回复尾部输出记忆块 | 实现 |
| 整理 / 补齐 | 会话当前模型，独立一次或分批调用 | 历史修复、手动补全 | 实现 |
| 独立自动抽取 | 用户指定的抽取模型 | 回复完成后另行调用 | 后续扩展 |

同回合模式不显示一个实际无效的“独立抽取模型”选择。未来增加独立模式时，输入必须覆盖用户与助手双方的有效正文，并处理等待、失败和覆盖缺口；它仍属于同一个记忆模块。

## 8. 一轮对话中的完整链路

~~~mermaid
flowchart TD
    A["准备回复"] --> B{"会话记忆开启？"}
    B -- 否 --> C["按普通上下文生成"]
    B -- 是 --> D{"有待整理历史？"}
    D -- 有 --> E["按保留正文整理"]
    E -- 成功 --> F["筛选记忆与抽取规则"]
    E -- 失败或取消 --> G["重试或关闭记忆继续"]
    D -- 无 --> F
    F --> H["生成正文与更新块"]
    H --> I{"正常完成且更新合法？"}
    I -- 是 --> J["随本轮提交记忆变更"]
    I -- 否 --> K["不提交非法记忆，保留处理结果"]
~~~

### 8.1 请求之前：读取与规则准备

1. 确认会话开关、世界类型、记忆有效性与当前历史位置。
2. 如果有历史变更或暂停期间的缺口，先完成必要整理。
3. 按召回策略选择当前有效条目。
4. 为需要抽取的类型载入内容规则，即使当前没有一条记忆被召回。
5. 组装“平台固定协议 + 预设通用任务规则 + 世界类型规则 + 本轮已召回记忆”。
6. 与当前状态、近期正文、适用摘要一起计入总上下文预算。

召回旧记忆与抽取新记忆分别判断。空记忆库必须能产生第一条记录。

### 8.2 模型生成：正文和明确的记忆处理结果

默认每个正常回合都允许判断是否需要记忆变化，但不要求每轮新增条目。

本轮开启抽取时，要求输出一组成对的 memory_update 标签，内部为操作记录；没有变化则输出完整空块。完整空块表示“已检查，无变化”，整个块缺失表示“未确认完成”，保留覆盖缺口。这样不把模型漏写与真正无变化混为一谈。关闭抽取的回合不要求该块，也不接受意外返回的写入。

内置规则应要求：

- 只记录已确认的经历、明确表达的信息，以及未来有用的变化。
- 区分用户意图、假设、角色说法和实际结果。
- 优先记录新增信息，不重复抄录整个世界卡和全部状态。
- 使用绝对或有剧情锚点的时间表述；不要把“明天”留成随当前轮漂移的含义。
- 对已召回的相同记录优先更新；无变化则无操作。
- 只处理已授权的类型和已有记忆 ID。

普通自动抽取依据本轮真实用户内容与完成的助手正文。世界设定、近期历史提供解释背景，不等于要求每轮重新抽取所有历史。开场参与首轮有效剧情材料，但创建会话本身不额外调用模型。历史补全使用明确的独立范围。

推理文本、行动建议、历史隐藏协议块、失效摘要不作为已发生事实来源。用于本轮叙事的旧记忆也不能被当作新增事实再次机械写入。

### 8.3 回复之后：校验与提交

- 仅在本轮开启记忆、生成正常结束且正文有效时处理记忆块。
- 正文、状态、建议与记忆块分别校验。记忆块失败不把已成功的正文判成整体失败，也不撤销有效状态结果。
- 半截输出或取消时不执行不完整记忆操作；保存了部分正文时，记忆覆盖范围保留缺口，之后可补齐。
- 先在内存形成记忆候选，再与本轮助手及相应处理回执在同一事务边界提交。
- 事务失败时不能出现“消息不存在，但它产生的记忆已生效”。
- 提交成功后才通知界面，下一轮才能召回本轮新记忆。
- 正常无操作记录为已处理；非法块记录失败并留下需要补齐的位置。

首版记忆操作按一个回合批次完整校验、整体提交，避免“移除旧条目成功，新增替代条目失败”的半套结果。它不要求现有状态更新也改成相同的批次策略。

## 9. 召回策略与预算

### 9.1 首版提供少数能解释清楚的方式

| 策略 | 行为 | 适用例子 |
|---|---|---|
| 常驻优先 | 优先放入少量长期重要信息 | 用户明确置顶的一条约定 |
| 关键词 / 关联对象匹配 | 当前输入及近期正文命中关键词或角色/地点等关联信息 | 再次提到林舟或码头 |
| 近期补充 | 按剧情产生位置选择最近的有效记录 | 接续最近发生的事情 |

世界类型可以选择或组合这些方式。无类型的通用记录默认“匹配优先 + 少量近期补充”。首版不把简单关键词筛选宣传成语义理解；向量召回与重排属于可替换的后续检索策略。

### 9.2 固定顺序

1. 先限定所属会话、当前剧情版本、有效类型。
2. 排除已撤下、来源失效和仍待整理的结果。
3. 按策略取候选，统一去重。
4. 在会话记忆预算内按优先级选取。
5. 注入带稳定 ID、类型和正文的条目，以便本轮精确更新。
6. 与其余上下文一起完成最终预算检查。

不使用召回出来的记忆继续递归触发更多记忆，首版保持一次有界选择。类型的条数限制与“常驻”都不能越过会话总预算；超额时按规则舍弃整条，并可在记忆面板查看本轮实际用了哪些内容。

按近期筛选使用剧情来源位置，不使用整理操作的机器时间；一次重整不能让所有旧事实突然变成“最近发生”。

没有命中、因预算没加载、类型近期条数以外，只表示本轮未使用，不意味着永久删除。

## 10. 更新协议：稳定 ID 的 add / update / remove

| 操作 | 语义 | 限制 |
|---|---|---|
| add | 新增一条记忆，由平台生成稳定 ID | 指定合法类型与内容，不能自行指定另一个会话 |
| update | 按 ID 替换单条正文及允许修改的内容字段，保留版本 | 目标必须是本轮已提供且授权的有效记录 |
| remove | 按 ID 将条目从当前有效集合撤下 | 保留必要历史用于回退；不等于物理抹除全部历史 |

**不按数组下标操作。** 召回会筛选、排序，某轮的第 3 条不是下一轮的第 3 条。

**不允许正常回合整体 replace。** 模型只看到部分已召回记忆，没有输出的旧条目应当保留，不能被隐式删除。

update 替换的是单条完整内容，通常比继续增加字符级/字段级 patch 更容易理解。复杂结构化状态仍交给状态模块。

示例中的类型仅为某张世界卡自定义，不是平台预置分类：

~~~text
add：增加“林舟曾把母亲留下的铜钥匙交给玩家，并请求保密。”
update m_17：改为“玩家已向船长透露钥匙来历，林舟尚不知情。”
remove m_23：撤下重复记录，保留 m_17。
~~~

对于同一 ID 的单次变化，尽量输出一个最终操作，不用“删除再新增”模拟更新。模型不能猜测未提供的 ID；服务端校验归属、版本和本轮授权范围，不信任模型输出的 worldId/sessionId。

相同来源、类型、内容的重复 add 可以确定性去重；文字不同但意思相同的重复并不能靠 ID 完全解决。首版通过“仅处理新增信息、提供已有匹配记录、人工整理”降低重复，不承诺完整语义去重。

完整替换当前有效视图仅用于平台控制的整理流程：明确处理范围、校验来源、保留有效人工修正、完成后一次发布。它不是开放给日常模型的整库操作。

## 11. 任意楼层修改、删除与重新生成

### 11.1 产品规则表

| 操作 | 记忆处理 | 是否需要模型 |
|---|---|---|
| 最新助手重新生成 | 先撤回旧助手的记忆变更，再由新助手产生新变更；若覆盖该回复的跨范围整理无法直接回退，则先整理保留区间；失败不恢复旧助手记忆 | 普通逐轮结果可直接撤回；跨范围修复与正常生成需要 |
| 删除纯尾部消息，没有后继剧情 | 恢复到保留历史对应的有效版本；若切到跨范围整理结果内部，按覆盖关系标记待整理 | 可直接恢复的情况不需要 |
| 修改最新正文 | 旧处理结果失效，需要按新正文补齐；不能继续相信旧数据块 | 补齐需要 |
| 修改或删除中间任意普通消息 | 找到最早影响位置，后缀自动记忆待整理 | 整理需要 |
| 同时删除多个不连续楼层 | 从最早影响位置统一判断，避免分别处理后留下污染 | 整理需要 |
| 修改 user 消息 | 与修改 assistant 同样检查；用户明确提供的信息也可能成为来源 | 视位置与影响决定 |
| 仅修改不参与事实的展示元数据 | 不扩大为剧情来源变化 | 不需要 |
| 删除会话或世界 | 在所属删除流程内删除关联记忆；不留下可被其他会话召回的孤儿记录 | 不需要 |

“消息身份”依据真实 ID 与内容版本，不依据可复用的 seq 或展示楼层号。只校验最新 tip 也不够：中间正文可以改变，而 tip 保持不变。

### 11.2 为什么不能只删除直接来源

第 10 楼写入一条事实，第 20 楼把它合并成另一条记忆，第 30 楼又据此更新。第 30 楼的记录即使直接来源是第 30 楼，仍可能受第 10 楼旧事实影响。

首版不建设精确依赖图，而采用保守规则：

1. 计算最早受影响位置。
2. 将该位置起依赖旧历史的自动处理结果标为失效。
3. 标记当前记忆待整理，停止把这份视图当作当前完整记忆召回。
4. 保留变更前的有效前缀作为整理起点。
5. 根据现存正文重新计算后缀。

**旧前缀只是重建起点，不保证适合作为现在的记忆。** 例如后续保留正文已写 NPC 死亡，退回早期“NPC 活着”的记录直接继续聊天，仍然会产生错误。

被判为失效的历史记录可以保留以供管理与回溯，但不得重新进入自动召回。

### 11.3 默认何时整理

- 保存编辑或删除时只做确定性的失效处理，不立即调用模型，允许用户连续修改多处。
- 界面提示“历史已修改，下次回复前将整理记忆”，可显示影响起点。
- 用户也可以在记忆面板提前点击“整理记忆”。
- **下一次在记忆开启的情况下生成回复前，自动整理所需范围；成功后才正常召回。**
- 用户可取消。失败或取消后不使用旧失效视图，可重试，或关闭记忆继续本次回复。

一次很早的历史改动可能增加下一次回复的等待与模型成本，必须有可见进度与取消入口。不为每次整理增加重复确认框，也不把它藏成一次无成本的普通保存。

### 11.4 整理的输入与提交

整理使用：有效前缀基线、受影响处起目前仍保留的正文、生效的类型规则，以及仍有效的人工修正。

不能再把旧后缀记忆、已失效摘要或旧自动操作作为事实输入。内容较长可以分批处理，全部候选先留在本次操作中，最后一次发布新当前视图；失败不发布半套新旧混合结果。运行期间复用同一会话写锁，提交前复核消息来源版本、实际 tip 与配置基准。

此流程只整理记忆，不重新生成故事、不重跑旧状态更新、不改写旧助手当年的处理回执，也不伪造每楼的新历史视图。

整理独立记录实际用量与结果。整理已经成功、随后叙事生成失败时，保留已提交的整理结果；重试不重复整理同一段已有效历史，统计中也不把辅助处理算作主回复调用。

SR 当前是先保存用户输入再准备上下文。若整理失败，本次输入可能已存在；“重试”或“关闭记忆继续”必须接着回答这条已保存输入，不能再追加同样的用户消息。自动修复范围截止于本次待回答输入之前，避免把用户这次尚未执行的意图提前作为历史事实。

### 11.5 删除来源，不代表相关事实从所有正文中消失

例如删除第 3 楼“获得金钥匙”，但第 8 楼仍写“使用金钥匙开门”。整理仍可能从第 8 楼提取钥匙相关经历。

这不等于读取了被删除的消息，而是保留正文还提供了证据。要让某件事从整条故事线消失，需要用户同步修改相关正文或明确修正记忆；本模块不自动修改后续台词和剧情因果。

未来如果增加真正的分支/回到某楼继续，分支必须继承分叉点的记忆，不能共享源会话之后的新事实。当前没有必要为此提前实现分支引擎。

## 12. 人工管理、世界详情与导出

### 12.1 查询入口

世界详情增加“查看记忆”入口，使用轻量面板或独立查询视图，保留现有详情主体与六个内容 Tab 的交互，不重做世界详情。

默认按会话区分，支持：

- 会话、世界自定义类型筛选。
- 正文关键词搜索。
- 当前有效 / 待整理 / 已撤下的管理视图。
- 查看来源楼层、最近变更和是否人工维护。
- 跳转到对应会话的来源消息；来源已删除时明确说明。
- 编辑、撤下、置顶、整理，以及单独清空。

会话设置同样可进入本会话的记忆列表，不要求每次回到世界库。运行中允许查询；记忆编辑、整理和消息变更遵守同一会话忙态。

世界详情的跨会话列表也要分别校验会话可访问范围，不能仅因为看得到世界就暴露无权访问的会话内容。

### 12.2 人工修改与置顶

人工修正与自动提取要能区分：

- 手动修正的同一条记录不能被下次模型无声覆盖。
- 置顶只提高召回优先级，不能把来源失效的记忆变成有效。
- 来源仍有效的人工修正应在整理后保留。
- 人工修正的来源也被删除或改变时，标为需要确认并暂停召回；允许用户明确确认为独立的人工设定。
- 手动撤下的记录不能仅因重放同一条旧自动操作就被恢复。

不能承诺“删除一条记忆”就永远不会再提取出同义信息。保留正文仍然包含事实时，模型可能重新判断它有价值。若以后提供“不要再记住这件事”，应是明确的排除意图功能，不把语义黑名单隐含在普通 remove 里。

### 12.3 导出与生命周期

- 世界卡导出携带记忆类型、内容规则与召回配置。
- 普通世界卡导出不自动携带各会话的玩家经历。
- 预设导出携带默认运行配置和提示词，不携带记忆条目。
- 运行记忆的备份属于会话数据导出；完整备份应包含版本与来源，不能把仅导出的当前列表称为完整历史备份。
- 删除世界/会话由其删除用例同步处理记忆数据；关闭、停用类型、未命中召回均不等于删除。

## 13. 最小实现范围与演进

### 首版必须形成完整闭环

1. 独立记忆领域与持久化，默认按会话隔离。
2. 世界定义可选类型、抽取规则和有限召回策略，旧卡有通用兜底。
3. 预设记忆模块、明确注入位置、会话独立开关与有效配置。
4. 主模型同回合更新，稳定 ID 的 add / update / remove。
5. 有界召回、总预算、当前状态权威和事实/意图区分。
6. 正常回复、失败、中断、无变化的覆盖记录。
7. 最新回复重生成同步撤回；历史修改/删除使记忆失效。
8. 手动整理与下次回复前必要整理，成功后一次切换当前视图。
9. 世界详情与会话内查询、人工修正、置顶、撤下、清空。
10. 导入导出、删除生命周期、会话锁及来源版本验证。

独立抽取模型、向量召回/重排、自动跨会话共享、精确依赖图、自动长期遗忘评分、第三方插件安装框架和逐楼重放都可以后置。它们不是保证首版故事一致性的前提。

与既有计划协调：

- 消息操作计划落地时，在同一跨模块用例中增加记忆失效，不把它塞进 Session Repository 的隐式副作用。

- docs/runtime 与 AGENTS 的真实契约在功能实施时更新，本次不把未实现能力写成现行规范。

## 15. 实施顺序与验收

### 实施顺序

1. 固定归属、来源版本、覆盖范围及历史变更语义，再确定存储。
2. 完成独立记忆读写、撤回、失效与整理；先保证有效性。
3. 接入世界定义、预设配置、会话开关、召回和同回合更新。
4. 接入消息编辑/删除/重生成及失败重试，打通完整闭环。
5. 增加管理入口、导入导出与交互反馈，补齐函数级验证。
6. 功能实际完成后更新运行契约，不将本计划当作已实现说明。

### 关键验收场景

| 场景 | 必须观察到的结果 |
|---|---|
| 同一世界、同一预设的两个会话 | 可以分别开关；不会读取彼此剧情 |
| 世界卡未定义类型，记忆库为空 | 仍可首次抽取通用记录 |
| 某类型本轮未召回旧记录 | 仍可按适用规则新增该类型记忆 |
| 只召回了两条、库存还有其他条目 | 未加载的旧条目不会因未输出而被删除 |
| add / update / remove 的非法目标 | 不跨会话写入，不按数组位置误删 |
| 正常输出完整空记忆块 | 标记本轮已处理，不增加重复条目 |
| 开启抽取却漏掉整个记忆块 | 标为未确认处理，保留缺口，不伪装成完整覆盖 |
| 坏标签、非法操作、模型中断 | 不提交非法记忆；正常正文/状态保持各自结果 |
| 消息提交失败 | 不存在脱离消息生效的记忆 |
| 最新回复重生成且新生成失败 | 旧助手的记忆已经撤下 |
| 最新回复属于跨范围整理的覆盖区间 | 无法直接恢复时先整理保留范围，不误用包含旧回复的结果 |
| 编辑中间 user 或 assistant | 后续自动记忆待整理，不继续注入旧视图 |
| 删除直接来源但后续已经合并更新 | 不仅删除直接条目，后缀也正确失效 |
| 多次连续编辑 | 合并影响起点；保存编辑不反复调用模型 |
| 整理分批失败或取消 | 不发布半新半旧的记忆视图 |
| 整理时来源版本变化 | 旧结果不能覆盖新故事 |
| 整理失败后重试或关闭记忆继续 | 复用已保存用户输入，不重复追加 |
| 保留后文仍明确重复被删事实 | 允许按现存证据提取，并能解释来源 |
| 暂停记忆后继续剧情再开启 | 先补齐缺口，不把暂停前视图假装成当前完整记忆 |
| 人工修正、置顶与来源删除 | 修正不被无声覆盖；置顶不能绕过失效 |
| 改类型名称或切叙事预设 | 不丢数据、不静默改归属、不自动共享 |
| 召回超预算 | 有界选取；不永久删除未使用条目 |
| 当前状态与历史描述不同 | 当前值按状态读取，历史记忆保留时间与原因 |
| 导出普通世界卡 | 有类型定义，没有玩家会话记忆 |
| 删除所属世界或会话 | 记忆按生命周期清理，不留跨会话可见的孤儿数据 |

以上是未来实现应验证的业务行为。本次文档工作只核对来源、方案一致性、文件保存与变更范围，没有执行真实模型、启动服务或声称功能测试通过。
